## 1. 冻结结论与发布判定

CLIENT-AUTH-01 冻结为独立 `client` 域中的 Device Code 授权流，并以设备本地不可导出或受平台安全存储保护的密钥证明持有权。Android 默认且首要算法是 `p256-es256`，私钥由 AndroidKeyStore 持有；桌面端可使用 `ed25519`。不得宣称 Android 设备普遍具备可靠的 AndroidKeyStore Ed25519 支持，也不得为了统一算法而把 Android 私钥降级为 Rust 可导出的文件密钥。

当前结论是 **NO-GO for release**。只有第 15 节全部停止条件解除，才能从“冻结参考”进入“已验证”。文档存在、表存在、HTTP 200、单元测试通过或某一平台能登录，都不能单独解除 NO-GO。

冻结后的核心不变量如下：

1. Client API 使用独立 origin、进程、issuer secret 和 10 分钟 access token；public/admin token 不得互换。
2. Device Code、高权限 token 交换、refresh 和每个已认证 client 请求都必须带 PoP；只拿到 bearer token 不足以调用 Client API。
3. PoP V1 对逐字节 HTTP 表达签名；Go、Rust、Kotlin 必须使用同一黄金向量，不得各自“等价实现”。
4. 每个请求的 nonce 在 PostgreSQL、租户 RLS 范围内唯一。nonce 写入、session/device 校验或数据库不可用时一律 fail closed。
5. refresh 单次轮换与响应重放记录在同一事务提交；网络丢失可在严格、短暂、同请求重放窗内安全取回完全相同的响应。
6. 任何跨租户父子关系都由 `(tenant_id, id)` 复合外键约束，不能只依赖应用 WHERE 或 RLS。
7. human user code 是低熵材料，只存带独立 pepper 的 HMAC；不得把明文 code 放入 URL、访问日志、审计摘要或错误消息。
8. 对任何已通过密码学验证的 PoP，nonce 与对应 poll/risk/撤销结果必须先在数据库提交，再发送成功或错误响应；不能以 HTTP 非 2xx 为由回滚防重放状态。
9. 匿名 Client 请求的 tenant 与 canonical origin 只由 TLS SNI 的静态可信路由映射决定；`Host` 仅用于与该映射做等值校验，绝不是 tenant 输入。

## 3. 协议和算法协商

### 3.1 算法标识

只允许下列精确、区分大小写的 wire identifier：

| 标识 | 密钥 | 签名 | 签名 wire encoding | 默认平台 |
|---|---|---|---|---|
| `p256-es256` | NIST P-256 | ECDSA with SHA-256 | IEEE P1363 固定 64 字节 `r || s`，并强制 low-S | Android |
| `ed25519` | Ed25519 | PureEdDSA | 固定 64 字节 raw signature | Windows/Linux/macOS 桌面 |

公钥统一使用 X.509 SubjectPublicKeyInfo DER，再以无 padding 的 base64url 编码，字段名 `public_key_spki_b64u`。服务端必须解析 SPKI 并确认算法/OID/曲线，不能只按长度接受任意 DER。

`p256-es256` 的 Kotlin AndroidKeyStore signer 通常得到 ASN.1 DER ECDSA 签名。平台适配层必须严格解析 DER、拒绝非最小编码、将 `r/s` 转为各 32 字节 P1363，并在发送前规范化为 low-S。Go/Rust 服务端只接受 P1363 low-S，不接受 DER，也不接受 high-S 的等价签名。

### 3.2 capability 协商

`GET /v1/device-auth/capabilities` 是唯一不需要 PoP 的 Client 认证入口，生产环境只允许 HTTPS。响应：

```json
{
  "proof_versions": ["v1"],
  "key_algorithms": ["p256-es256", "ed25519"],
  "defaults": {
    "android": "p256-es256",
    "desktop": "ed25519"
  },
  "public_origin": "https://client.example.com",
  "authorization_expires_in": 600,
  "poll_interval": 5,
  "access_token_expires_in": 600
}
```

客户端按平台默认值选择算法；失败时不得静默回退到另一算法。显式不支持返回 `422 validation_failed`，用户重新选择或升级客户端后再发起新的 authorization。服务端不得在同一 authorization 中改算法或替换公钥。

AndroidKeyStore `p256-es256` 是冻结默认。Android Ed25519 只有在受支持设备/API/provider 矩阵经过真实验证，并另行更新 capability 后才能启用；本文不作广泛兼容承诺。

## 4. PoP Canonical V1：逐字节冻结

### 4.1 HTTP headers 与 Authorization 唯一表示

每个 PoP 请求必须包含：

```text
X-Aegis-Proof-Version: v1
X-Aegis-Key-Algorithm: p256-es256 | ed25519
X-Aegis-Key-Id: <SHA-256(SPKI DER), base64url no padding>
X-Aegis-Timestamp: <Unix seconds decimal>
X-Aegis-Nonce: <16 random bytes, base64url no padding>
X-Aegis-Proof: <signature, base64url no padding>
```

timestamp 必须是无符号十进制 Unix 秒，不允许 `+`、前导零、空白或小数。允许时钟偏差为 `[-120,+120]` 秒。nonce 解码后必须恰好 16 字节；每次 HTTP 尝试生成新 nonce，包括 refresh 响应丢失后的安全重试。

header cardinality 与字节规则冻结如下：

- 上述六个 `X-Aegis-*` header 各自必须恰好出现一次。任何重复 header、逗号合并值、obs-fold、值前后空白、非 ASCII 值或代理合并痕迹均返回 `400 malformed_request`，在进入密码学验证前停止。
- capability、创建 authorization、Device Code token exchange、refresh 端点必须 **没有** `Authorization` header；即使同时提供了可解析 token 也拒绝为 `400 malformed_request`。
- 每个 access-token PoP 请求必须恰好有一个、且仅一个 HTTP field line：`Authorization: Aegis-PoP <token>`。scheme 大小写敏感并固定为 ASCII `Aegis-PoP`；scheme 后恰好一个 `SP` (`0x20`)；不得有前后空白、HTAB、逗号、第二个 credential 或第二条 Authorization field line。
- `<token>` 是 JWT compact serialization 的 ASCII bytes：恰好三个非空 base64url-no-padding segment，以两个 `.` 分隔；只允许 `[A-Za-z0-9_-]` 与分隔点。解析层不得先 trim、大小写折叠、percent-decode 或重编码。
- `ath` 对 `<token>` 的逐字节 ASCII 求 SHA-256，**不含** `Aegis-PoP`、空格、header 名、冒号或 CRLF。token 校验器与 PoP verifier 必须消费同一份 parser 返回的不可变 token byte slice。
- HTTP/2/HTTP/3 的重复字段即使框架已合并也必须由边缘层拒绝；可信边缘不得把多个 Authorization 值折叠成应用无法辨认的单值。

### 4.2 origin、request target 与 body

- `origin` 来自第 4.6 节 TLS 路由表中的 `public_origin`，格式为小写 scheme/ASCII authority：`https://host[:non-default-port]`。生产只允许 `https`；默认 443 不写端口。
- 服务端绝不能用未校验的 `Host`、`Forwarded` 或 `X-Forwarded-*` 构造 canonical origin 或 tenant。任何 forwarded host/proto/tenant header 一律忽略并在入口删除；`Host` 只与 TLS 路由表的 expected authority 做严格校验。
- `target` 为 Go `URL.EscapedPath()` 的原始 escaped path；若 `RawQuery` 非空，则逐字节拼接 `?` + `RawQuery`，不解码、不排序、不把 `+` 改为空格。
- Device Code、token、refresh、logout、approve/deny 等认证端点 **拒绝任何 query string**。其他 Client GET 若使用 query，客户端必须签名实际发送的 RawQuery；代理不得重排参数。
- `Content-Encoding` 缺失或精确为 `identity` 才允许。`gzip/br/deflate` 一律 `415`，避免客户端签压缩前、服务端验压缩后的歧义。
- `body-sha256` 对 HTTP transfer framing 解码后、content coding 之前的实际 body bytes 求 SHA-256。由于只允许 identity，它等于 handler 读取的原始 body。无 body 使用 SHA-256(empty)。
- JSON 不做语义 canonicalization。Rust 先产生最终 UTF-8 JSON bytes，再由 Kotlin/HTTP 层原样发送；任一层不得重新序列化、换行或改空白。

### 4.3 credential kind 与 `ath`

`credential-kind` 只允许：`none`、`device_code`、`access_token`、`refresh_token`。`ath` 是相应明文 credential 的 SHA-256，再以 base64url no padding 编码：

| 场景 | credential-kind | ath |
|---|---|---|
| 创建 authorization | `none` | 空串 |
| 轮询/交换 Device Code | `device_code` | SHA-256(device_code UTF-8 bytes) |
| refresh | `refresh_token` | SHA-256(refresh_token UTF-8 bytes) |
| 已认证 Client API | `access_token` | SHA-256(`<token>` 的精确 ASCII bytes，不含 scheme/SP) |
| capability | 无 PoP | 不适用 |

body 内出现同一 credential 时，`ath` 仍必须存在；二者任何不一致都统一返回 `401 invalid_proof`。

Authorization/ath parser 向量（仅验证字节边界，不是有效 HMAC token）：

```json
{
  "vector_id": "authorization-ath-v1-01",
  "authorization_field_value_ascii": "Aegis-PoP eyJhbGciOiJIUzI1NiJ9.eyJqdGkiOiJ0ZXN0In0.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "token_ascii": "eyJhbGciOiJIUzI1NiJ9.eyJqdGkiOiJ0ZXN0In0.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "ath_b64u": "rMZwtCN7i0t0D7XndL0AT3C3S4AqlUyPi5C_mpS5FGU",
  "negative_field_values": [
    "Bearer eyJhbGciOiJIUzI1NiJ9.eyJqdGkiOiJ0ZXN0In0.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
    "Aegis-PoP  eyJhbGciOiJIUzI1NiJ9.eyJqdGkiOiJ0ZXN0In0.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
    "aegis-pop eyJhbGciOiJIUzI1NiJ9.eyJqdGkiOiJ0ZXN0In0.AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA"
  ]

```

### 4.4 canonical bytes

待签名字节是以下 ASCII/UTF-8 字段，字段名小写，值后不允许空格，每行以单字节 LF (`0x0A`) 结束，最后一行后也必须有 LF；禁止 CRLF 和 BOM：

```text
AEGIS-DEVICE-POP-V1\n
origin:<origin>\n
method:<UPPERCASE HTTP METHOD>\n
target:<EscapedPath[?RawQuery]>\n
timestamp:<unix seconds>\n
nonce:<base64url no padding>\n
body-sha256:<base64url no padding>\n
credential-kind:<kind>\n
ath:<base64url no padding or empty>\n
```

签名规则：

- `p256-es256`：对上述 canonical bytes 执行 SHA-256，再 ECDSA P-256；输出 P1363 low-S 64 字节。
- `ed25519`：直接对上述 canonical bytes 执行 Ed25519；不得先自行 SHA-256。

### 4.5 冻结 canonical 黄金向量

输入 body 的逐字节 UTF-8 为：

```json
{"device_code":"dc_test_7Zx","grant_type":"urn:ietf:params:oauth:grant-type:device_code"}
```

预期值：

```text
body_sha256_b64u = juuyy3R-1MzM12fkCAwimsZGELRhsrRs37SM062Q_2g
ath_b64u         = L6VoES3PKjH6XxqQXxRcHbKrdUJWMWserESwHoy2V08
```

canonical UTF-8（代码块末尾包含一个 LF）：

```text
AEGIS-DEVICE-POP-V1
origin:https://client.example.com
method:POST
target:/v1/device/token
timestamp:1785398400
nonce:AAECAwQFBgcICQoLDA0ODw
body-sha256:juuyy3R-1MzM12fkCAwimsZGELRhsrRs37SM062Q_2g
credential-kind:device_code
ath:L6VoES3PKjH6XxqQXxRcHbKrdUJWMWserESwHoy2V08
```

```text
canonical_sha256_b64u = enFUTCTzK2Ukojk0Bi6saGwd3n3Hhg-Tz0s4nf3jH1A
```

实现前由 Security owner 提交唯一共享的 `testdata/device_pop_v1_vectors.json`，至少包含上面的 canonical vector、一个 `p256-es256` SPKI/P1363-low-S 签名正向量、一个 `ed25519` SPKI/raw 签名正向量，以及 CRLF、high-S、DER、query 重排、body 空白变化等负向量。Go、Rust、Kotlin 测试必须读取同一文件；禁止把同样常量复制到三个语言目录。签名正向量没有经过三语言交叉验证前，停止实现合并。

P-256 验收是数学验签，不是“重新签名后字节相等”。普通 ECDSA signer 可为同一 key/message 产生不同的合法 `r`；实现必须验证 `ECDSA.Verify(public_key, SHA-256(canonical_bytes), r, s)`、`1 <= r,s < n` 且 `s <= n/2`。黄金向量中的固定 64 字节签名只是一个合法样本；只有显式使用固定私钥与 RFC 6979 deterministic nonce 的向量生成器才允许断言签名字节相等，AndroidKeyStore 运行时测试只能断言格式、low-S 与验签成功。

### 4.6 三类 request hash 与可信路由

nonce 审计 hash、refresh 响应重放 hash 和 Device Code issuance 响应重放 hash 是三个不同协议字段，禁止复用名称、函数或域：

```text
nonce_request_hash =
  SHA-256(ASCII("AEGIS-NONCE-REQUEST-V1") || 0x00 || canonical_bytes)
```

它包含本次尝试的 timestamp/nonce，因此每个 retry 都不同，写入 `device_proof_nonces.request_hash`。现有第 4.5 节 canonical 向量对应：

```text
nonce_request_hash_b64u = AKyL-EmlDrl-bVouj2CGGkakozEDfQni9uSNdsJaSHI
```

refresh 重放匹配使用不含 timestamp、nonce、signature 的稳定记录，所有值均为已严格解析的 ASCII，末行也有 LF：

```text
AEGIS-REFRESH-REPLAY-REQUEST-V1
origin:<trusted origin>
method:POST
target:/v1/auth/refresh
body-sha256:<SHA-256(exact body bytes), b64u>
credential-kind:refresh_token
ath:<SHA-256(exact refresh token ASCII bytes), b64u>
key-id:<32-byte SPKI fingerprint, b64u>
refresh-request-id:<lowercase canonical UUIDv7>
```

`refresh_replay_request_hash=SHA-256(上述完整 UTF-8/LF bytes)`，写入 replay 表的 `replay_request_hash`；不得把 `nonce_request_hash` 或 PoP signature 当作 retry 等价键。`body_hash` 如单独保存，固定为裸 `SHA-256(exact body bytes)`，列名必须与两个 request hash 区分。

Device Code issuance 重放匹配使用第 18.1 节的 length-prefixed `stable_record_bytes`，其结果列名固定为 `stable_request_hash`。它同样排除 timestamp、nonce 和 signature，但其域标签、字段集合与编码都不同于 refresh 的 LF 文本记录；三种 hash 必须由三个具名函数产生。任何数据库列、DTO 或测试向量都不得把 `nonce_request_hash`、`refresh_replay_request_hash` 和 `stable_request_hash` 互换。

匿名 tenant/origin 解析冻结为直接 TLS 模式：Client gateway 自己终止 TLS，不接受明文上游或 TLS 终止代理。启动时加载不可热改的映射 `lowercase ASCII SNI -> {tenant_id, public_origin, expected_authority}`；SNI 必须是无尾点 DNS 名且唯一命中。HTTP `Host` 解析后必须无 userinfo、无尾点、无非默认端口歧义，并与 `expected_authority` 逐字节相等；未知 SNI、缺 SNI、Host 不匹配或同 SNI 多租户配置均在读取认证 body 前返回 `421 misdirected_request`。tenant RLS context、capability 的 `public_origin`、PoP canonical origin 和 JWT expected issuer 全部取自同一个不可变 route object。正式域名可以在部署配置中替换示例值，但该解析算法没有 UNKNOWN；若部署必须在反向代理后终止 TLS，须先另立并评审 transport-attested route contract，本冻结稿不允许用 forwarded header 兼容。

## 5. Device Code 状态机

```text
pending ──approve──> approved ──consume once──> consumed
   │                    │
   ├──deny──────────> denied
   └──timeout────────> expired
```

冻结规则：

- `pending` 初始有效期 600 秒；`expires_at <= transaction_timestamp()` 时不能 approve/deny/consume。
- approve/deny 只能由同租户、public audience 的登录用户执行，并要求 15 分钟内 recent reauth。
- `approved` 只绑定 user，不签发 credential；持有对应私钥的设备完成 token exchange 后才创建/激活 device、session 和 refresh family。
- `approved -> consumed` 必须用 `SELECT ... FOR UPDATE` 或等价条件更新，在同一事务内完成 proof nonce 插入、设备配额判断、device/session/refresh 创建与 `consumed_at` 写入。
- 所有终态不可逆。后台可物化 `expired`，但每个写入口仍必须按数据库时间自行拒绝过期行。
- 同 authorization 并发 approve/deny/consume 只有一个合法状态转换，其余返回稳定冲突/无效授权，不得重复发 token。
- 设备重装或换钥必须创建新的 authorization/key version；不得在已有 active device 上静默替换公钥。

## 6. API 冻结

所有响应继承现有 `X-Request-ID`、JSON error envelope 和 `Cache-Control: no-store`。认证 secret 不进入 URL。

### 6.1 创建 authorization

`POST /v1/device/authorizations`，anonymous + body 内公钥 PoP。

```json
{
  "proof_version": "v1",
  "key_algorithm": "p256-es256",
  "public_key_spki_b64u": "...",
  "platform": "android",
  "arch": "arm64-v8a",
  "os_version": "...",
  "app_version": "...",
  "config_schemas": ["sing-box/v1"],
  "update_channel": "stable",
  "friendly_name": "Pixel"
}
```

201：

```json
{
  "authorization_id": "uuid",
  "device_code": "256-bit-base64url-secret",
  "user_code": "ABCD-EFGH",
  "verification_uri": "https://portal.example.com/device",
  "verification_uri_complete": "https://portal.example.com/device#user_code=ABCD-EFGH",
  "expires_in": 600,
  "interval": 5
}
```

`verification_uri_complete` 只使用 URL fragment；fragment 不发送到服务器。portal 从 fragment 读出后必须从地址栏清除，并把 code 放入 POST body。

### 6.2 human code 查询和决定

为避免反向代理访问日志记录 code，不使用 `/{user_code}` 路由：

- `POST /v1/me/device-authorizations/lookup`
- `POST /v1/me/device-authorizations/approve`
- `POST /v1/me/device-authorizations/deny`

三者都属于 public 域，要求 authenticated user；approve/deny 额外要求 recent reauth。请求：

```json
{"user_code":"ABCD-EFGH","authorization_id":"uuid"}
```

lookup 200 只返回待确认展示字段：

```json
{
  "authorization_id":"uuid",
  "platform":"android",
  "app_version":"...",
  "friendly_name":"Pixel",
  "key_algorithm":"p256-es256",
  "key_fingerprint":"sha256:short-display",
  "expires_at":"RFC3339"
}
```

不存在、过期、错误租户和错误 code 返回相同 404；approve/deny 成功 204。响应和审计都不回显 human code。

### 6.3 Device Code token exchange

`POST /v1/device/token`，anonymous + authorization 存储公钥 PoP：

```json
{
  "grant_type":"urn:ietf:params:oauth:grant-type:device_code",
  "device_code":"..."
}
```

状态：

| 条件 | HTTP / code | 行为 |
|---|---|---|
| pending 且轮询合规 | `400 authorization_pending` | 返回当前 `interval` |
| 快于 interval | `429 slow_down` | `Retry-After` 为实际秒数，interval 每次 +5，最大 30 |
| denied | `403 access_denied` | 不签发 token |
| expired/invalid，或 consumed 但不满足 replay 等价条件 | `401 invalid_grant` | 统一文案，不暴露命中情况 |
| consumed 且满足第 18.1 节 replay 等价条件 | `200` | 新 nonce 先提交；解密并重放已提交的逐字节相同 issuance response，不再签发 credential |
| approved + proof 有效 | `200` | 原子 consume、签发 credential，并在 commit 前持久化完整加密响应 envelope |

成功响应：

```json
{
  "access_token":"...",
  "token_type":"Aegis-PoP",
  "expires_in":600,
  "refresh_token":"...",
  "refresh_expires_in":2592000,
  "scope":"client:profile:read client:subscriptions:read client:config:read client:device:self",
  "device_id":"uuid",
  "session_id":"uuid"
}
```

### 6.4 refresh

`POST /v1/auth/refresh`，refresh token PoP：

```json
{"refresh_token":"...","refresh_request_id":"uuid-v7"}
```

同一设备每次网络重试保留相同 `refresh_request_id` 和完全相同 body bytes，但生成新的 PoP nonce/signature。成功返回与 token exchange 相同形状，并轮换 refresh token。第 8 节定义响应丢失重放语义。

`refresh_request_id` 必须是 RFC 9562 UUIDv7 的 36 字符小写 canonical 文本；解析后 version 必须为 7、variant 必须为 `10`，不得接受大写、无连字符、URN 或 brace 形式。

### 6.5 logout 与设备撤销

- Client `POST /v1/auth/logout`：access-token PoP，撤销当前 session 和 refresh family，204。
- Public `POST /v1/me/devices/{device_id}/revoke`：登录用户 + recent reauth；同事务撤销 device、其所有 client sessions/refresh families、设备范围订阅 credential，204。
- wrong tenant/wrong owner/nonexistent 统一 404。撤销后每个 Client 请求立即失败，不等待 access token 过期。

### 6.6 有效 PoP、非 2xx 与提交顺序

处理器必须返回内部 typed outcome；HTTP writer 只能在数据库 commit 成功后观察该 outcome。冻结类型和持久化义务：

| typed outcome | HTTP | commit 前必须持久化 |
|---|---|---|
| `device_token_issued` | `200` | nonce + device/session/refresh/JTI + consumed 状态 + 第 9.8 节完整加密 issuance response；response serialization 与 replay INSERT 均在 commit 前完成 |
| `business_success` | `2xx` | nonce + 完整业务状态；非 issuance token 的普通响应可在 commit 后由无 secret 的 typed DTO 序列化 |
| `authorization_pending` | `400` | nonce、`last_polled_at`、`poll_count` |
| `slow_down` | `429` | nonce、`last_polled_at`、`poll_count`、增加后的 interval |
| `access_denied` / `expired_grant` / `invalid_consumed_grant` | `403`/`401` | nonce；需要时物化 terminal 状态；合格 consumed retry 必须在此前分流为 `device_issuance_replay`；同事务 `audit_events`/`risk_events` |
| `refresh_replay` | `200` | 新 nonce、replay 使用计数/时间；响应仍取既有 ciphertext |
| `device_issuance_replay` | `200` | 新 nonce、issuance replay 使用计数/时间；响应只取既有 ciphertext，不再走普通轮询或签发 |
| `refresh_reuse_compromise` / `replay_decrypt_failed` | `401 invalid_grant` | 新 nonce、整 family compromised、session revoked、`audit_events`/`risk_events` |
| `authenticated_rejection`（scope/业务校验/冲突） | 对应 `4xx` | nonce + 必需 `audit_events`/`risk_events`；不得执行被拒绝业务写入 |

只有 header/canonical/签名/timestamp/credential 绑定尚未通过的 `malformed_request`/`invalid_proof` 不产生“有效 PoP nonce”行。若根据 device code/refresh hash 找不到可用于验签的存储公钥，则不能宣称 proof 有效；统一外部错误且用恒定路径防探测。

事务模板固定为：解析但不回写 → 建立 tenant transaction → 锁定 proof 所属 key/credential → 密码学验证 → 插入 nonce → 计算 typed outcome 并写上述安全状态及现有 `audit_events`/`risk_events` → 对 `device_token_issued` 在事务内完成 status、允许 headers 和 exact body 的最终序列化、AEAD 加密及 replay INSERT → `COMMIT` → 发送已经冻结的响应 bytes。要求风险事件的 outcome 若无法写入持久表，整个事务失败；异步 alert 可另行使用 outbox，但不能代替风险事实行。commit 失败一律丢弃原 outcome，返回 `503 security_state_unavailable` + `Retry-After: 1`，不得发送原 2xx/4xx，也不得把内存 audit 当成已持久化。连接在 commit 后、发送前断开不改变已提交状态；Device Code 客户端以同请求 body、同 device/key 和新 nonce 重试并走第 18.1 节 issuance replay，绝不继续普通 polling；refresh 客户端走第 8.3 节安全重放。

## 7. Access token、claims 与默认拒绝

### 7.1 独立 issuer

Client gateway 必须构造独立 issuer：

- JWT signing 只来自第 18.3 节 `AEGIS_CLIENT_JWT_KEYRING_JSON`；任何 legacy 单值 Client JWT secret 配置都不属于本契约，若仍配置则 Client gateway 拒绝启动，禁止静默导入或回退；
- `iss` 不再由请求拼接；它必须逐字节等于第 4.6 节可信 route object 的 `public_origin`。示例 route 的 issuer 是 `https://client.example.com`，无尾随 `/`；
- 独立 TTL 配置：`AEGIS_CLIENT_ACCESS_TOKEN_TTL=10m`；生产启动时大于 10 分钟或非正值直接失败；
- public/admin 的通用 `AEGIS_ACCESS_TOKEN_TTL` 不得控制 Client token；
- access token 只在内存和响应中出现，数据库不存明文。

JWT protected header 精确为 `{"alg":"HS256","kid":"cljwt_00000001","typ":"JWT"}` 的语义集合，其中示例 `kid` 遵守第 18.3 节无冒号 ASCII grammar，并由唯一 active key 条目提供；JSON key 不得重复，`alg`/`typ` 必须精确匹配，`kid` 必须逐字节命中只含 Client keys 的 keyring。拒绝 `none`、public/admin key、缺失/未知 `kid`、任何 `crit` 和任何 key fallback。verify-only 保留和删除门只按第 18.3 节数据库引用与轮换公式执行。

### 7.2 必需 claims

```json
{
  "iss":"https://client.example.com",
  "sub":"user_uuid",
  "tid":"tenant_uuid",
  "sid":"session_uuid",
  "did":"device_uuid",
  "aud":"client",
  "knd":"device",
  "cnf":{"aegis_spki_sha256":"base64url_sha256_spki"},
  "scp":["client:profile:read"],
  "jti":"base64url-of-exactly-16-random-bytes",
  "iat":1785398400,
  "exp":1785399000
}
```

claim schema 冻结为：`iss/sub/tid/sid/did/aud/knd/jti` 是非空 JSON string；`tid/sub/sid/did` 是小写 canonical UUID；`aud` 必须是 string `client`，不接受 audience array；`knd` 必须是 `device`；`cnf` 必须是只含 `aegis_spki_sha256` 的 object，该值 base64url 解码后恰好 32 字节；`scp` 是无重复、按 ASCII 升序的非空 string array；`iat/exp` 是可精确表示的整数 NumericDate，`exp-iat` 必须在 `(0,600]`。JWT payload JSON key 重复、类型强转、未知 claim 或任一格式错误都默认拒绝。

`jti` 是 issuer 生成的 16 个 CSPRNG bytes 的 base64url-no-padding（固定 22 ASCII 字符），每个新 access token 生成一次；它在该 token 的所有请求中保持不变，**不是** PoP nonce，也不能替代 nonce 表。签发事务必须先插入 `client_access_token_jtis(tenant_id,issuer,jti_hash,session_id,device_id,signing_kid,signing_key_version,issued_at,expires_at)`，其中 `jti_hash=SHA-256(raw 16 jti bytes)`，`signing_kid/version` 精确记录实际 active JWT key，并以 `(tenant_id,issuer,jti_hash)` 唯一；碰撞只允许在同一未提交事务中重新生成。每请求必须确认登记行、session/device/expiry、JWT header kid 与 registry signing kid/version 全匹配且未 revoked；保留至 `exp+120s` 后才可由受限清理角色删除。refresh/issuance replay 返回原 access token，因此返回原 jti，不插入第二行。启动和轮换 preflight 必须查询全部未到清理时间的 JTI signing kid/version；配置 keyring 缺任一引用 key 时拒绝启动/轮换。

允许 scope 仅为服务端 allowlist 与 token `scp` 的交集：

- `client:profile:read`
- `client:subscriptions:read`
- `client:config:read`
- `client:device:self`
- `client:usage:write`（仅在对应 API 实现后可签发）

禁止 admin、billing mutation、跨设备和 token 管理 scope。

### 7.3 每请求验证顺序

每个 Client authenticated request 必须在同一个 tenant-scoped DB transaction 中：

1. 校验 JWT header/HMAC、route-derived exact `iss`、`aud=client`、`knd=device`、完整 claim schema、`exp/iat`；
2. 校验 PoP、`ath`、timestamp、算法/key id；
3. 插入 nonce 唯一行，冲突即 replay；
4. 查询 jti registry：tenant/issuer/session/device/jti/expiry 全匹配且未撤销；
5. 查询 session：tenant/user/device/audience 全匹配，未撤销且未过期；
6. 查询 device：tenant/user/id 全匹配，状态 active，公钥 fingerprint=`cnf.aegis_spki_sha256`；
7. 校验 endpoint 所需 scope；
8. 执行业务查询/写入，并按第 6.6 节提交 typed outcome。

任何数据库错误、nonce insert 错误、查无行或字段不一致均 fail closed。不能因为 Redis、缓存或审计系统异常跳过上述强校验。

## 8. Refresh family、原子轮换与响应丢失

### 8.1 生命周期

- refresh token 为至少 32 随机字节 base64url；数据库只存 SHA-256 hash。
- absolute lifetime 30 天；idle lifetime 7 天，每次成功轮换更新 family 的 last-used 语义。
- 每个 token 属于唯一 `family_id` 和递增 `generation`；同一 family 最多一个 `active` token。
- active token 成功使用后在同事务变为 `rotated` 并指向新 token；revoked/compromised 永不恢复。
- 已 rotated token 在安全重放窗外再次出现，或请求 id/body/device 不匹配，立即把整个 family 与 session 标为 compromised/revoked，并写 risk/audit。

### 8.2 首次 refresh 的单事务步骤

1. 验 PoP 并插入 nonce；
2. `SELECT refresh_token ... FOR UPDATE`，校验 active、family、session、device、绝对/空闲过期；
3. 生成新 refresh secret、10 分钟 access token 和完整响应 bytes；
4. 插入 `generation+1` 的新 refresh hash；
5. 老 token 更新为 rotated/replaced_by；
6. 以 server envelope key 加密完整响应 bytes，连同 `refresh_request_id`、第 4.6 节 `body_hash` 与 `replay_request_hash`、old/new token id、device/key fingerprint、过期时间写入 replay 表；
7. 提交后才发送响应。

任一步失败则事务回滚，老 refresh 保持 active；不能出现“老 token 已失效但新 secret 无法取回”的半提交。

### 8.3 响应丢失安全重放窗

安全窗固定 30 秒，从首次事务最后一条 SQL 写 replay row 时的数据库 `statement_timestamp()` 计算；该 INSERT 必须是 commit 前最后一条语句，应用随后立即 commit。客户端重试必须：

- 使用同一个 old refresh token；
- 使用同一个 `refresh_request_id`；
- body bytes/hash 完全相同；
- 由同一 device key 签名，`ath` 相同；
- 使用全新的、未见过的 PoP nonce；
- 在 replay row 的 `expires_at` 前到达。

服务端锁定老 token 后若发现它已 rotated，只在上述条件全部成立时解密并返回**逐字节相同**的既有响应，不再生成 token、不增加 generation。条件不符或超过 30 秒按 refresh reuse compromise 处理。replay ciphertext 到期后可清理；清理失败不能恢复 credential，只增加加密存储保留时间并告警。

refresh hash 的机器可验证向量如下；`body_utf8` 不含末尾 LF，`stable_record_utf8` 最后一行含 LF：

```json
{
  "vector_id": "refresh-replay-v1-01",
  "refresh_token_ascii": "rt_test_AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8",
  "refresh_request_id": "01981f36-4c00-7abc-8def-0123456789ab",
  "key_id_b64u": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA",
  "body_utf8": "{\"refresh_token\":\"rt_test_AAECAwQFBgcICQoLDA0ODxAREhMUFRYXGBkaGxwdHh8\",\"refresh_request_id\":\"01981f36-4c00-7abc-8def-0123456789ab\"}",
```

## 9. 数据模型和 SQL 约束冻结

实现迁移建议使用集成时的下一可用编号（不得低于 `00042`），例如 `migrations/00042_client_device_auth.sql`；编号仍须由集成 owner 根据落地时最新 migration 串行确认。以下是结构约束，不表示迁移已存在。

### 9.1 复合租户外键

所有父表先有 `UNIQUE (tenant_id,id)`；FK 的 `ON DELETE` 行为保持下表决定。以下是 `00002_identity.sql`、`00007_client_delivery.sql`、`00018_subscription_delivery.sql`、`00019_subscription_token_vault.sql` 中所有仍可能被 Client 路径消费的 UUID 关系清单，不允许实现者再自行猜测：

| 子关系 | 冻结决定 |
|---|---|
| `devices(tenant_id,user_id) -> users(tenant_id,id)` | 已是复合 FK，保留 |
| `device_authorizations(tenant_id,user_id) -> users` | nullable；新增复合 FK，只有 approved/consumed 可非空且这些状态必须非空 |
| `device_authorizations(tenant_id,device_id) -> devices` | nullable；替换裸 FK 为复合 FK，只有 consumed 必须非空 |
| `device_tokens(tenant_id,device_id/user_id) -> devices/users` | 若保留 `kind=config`，两条都改复合 FK；所有 `kind=refresh` 撤销并禁建 |
| `device_tokens(tenant_id,device_id,replaced_by) -> device_tokens(tenant_id,device_id,id)` | `kind=config` 链保留并强制同 tenant、同 device；旧 refresh 链不迁移 |
| `subscription_credentials(tenant_id,subscription_id,user_id) -> subscriptions(tenant_id,id,user_id)`；nullable `(tenant_id,device_id,user_id) -> devices(tenant_id,id,user_id)` | 父表须有这些复合 UNIQUE；DB 直接证明 credential、subscription、device 是同 tenant/同 user，device nullable 仍受 scope CHECK |
| `credential_access_log(tenant_id,credential_id) -> subscription_credentials` | 替换裸 FK 为复合 FK |
| `credential_access_log(tenant_id,config_bundle_id) -> config_bundles` | nullable；补复合 FK。因建表顺序靠前，迁移在 `config_bundles` 约束建立后 `ALTER TABLE` 添加 |
| `config_bundles(tenant_id,subscription_id,user_id) -> subscriptions(tenant_id,id,user_id)`；始终生效的 `(tenant_id,credential_id,subscription_id,user_id) -> subscription_credentials(tenant_id,id,subscription_id,user_id)`；双方 non-NULL generated `device_binding_key` 参与第二条五列 FK；nullable `(tenant_id,device_id,user_id) -> devices(tenant_id,id,user_id)` | active bundle 要求 credential_id NOT NULL；generated key 把 NULL 固定编码为 subscription scope、非 NULL 编码为 device UUID，避免 `MATCH SIMPLE` 跳过 device 同一性；数据库锁定完整链并禁止同用户跨设备拼接 |
| `config_bundles.node_ids[] -> nodes.id` | UUID array 不能安全表达 tenant FK；新建 `config_bundle_nodes(tenant_id,bundle_id,node_id)`，两条复合 FK 分别指向 bundle/nodes，校验并切读后删除/停止读取 `node_ids` |
| `client_releases.tenant_id -> tenants.id` | 无其他 UUID 父关系，保留 |
| `sessions(tenant_id,user_id/device_id) -> users/devices` | user 复合 FK 收紧；device 对 client audience 必须非空并加复合 FK，public/admin 可空 |
| `refresh_families(tenant_id,session_id,user_id,device_id) -> sessions` | 第 9.4 节以 session 的 tenant/id/user/device 复合键一次绑定整个 family |
| `refresh_tokens(tenant_id,session_id/user_id) -> sessions/users` | 两条都替换为复合 FK |
| `refresh_tokens` parent/replaced_by | 按第 9.4 节强制同 tenant、同 family |
| `client_access_token_jtis(tenant_id,session_id,device_id) -> sessions(tenant_id,id,device_id)` | 使用一个三列复合 FK 证明 JTI 的 session/device 同一性，不接受两个独立 FK 替代 |
| refresh replay old/new token、session、device | 按第 9.4 节使用带 family/tenant 的复合 FK |

`subscription_fetch_log.credential_id/subscription_id` 按 `00018` 的保留审计目的继续作为可空、非权威 opaque UUID label，不得被 JOIN 后用于认证、授权、tenant 推导或资源存在性判断，因此不属于存活业务 FK；其 tenant 只来自写入时已认证 context。`00019` 只新增 `subscription_credentials.token_encrypted`，没有新关系。`00007` 注释提到 `client_capabilities`，但实际未建表，不得虚构 FK。`api_tokens.audience='client'` 不是本契约 credential authority：迁移时撤销现有此 audience token、禁止新建，Client gateway 永不接受。

任何未出现在这份清单、但迁移预检发现由 Client 路径读取的 `*_id`/UUID array 都使 cutover 停止；必须先修订冻结契约。nullable FK 只能在上表明确允许时为空。

### 9.2 device authorization 约束

至少增加/收紧：

```sql
key_algorithm text CHECK (key_algorithm IN ('p256-es256','ed25519'))
public_key_spki bytea NOT NULL
key_fingerprint bytea NOT NULL CHECK (octet_length(key_fingerprint)=32)
user_code_mac bytea NOT NULL CHECK (octet_length(user_code_mac)=32)
device_code_hash bytea NOT NULL CHECK (octet_length(device_code_hash)=32)
approved_at, denied_at, consumed_at timestamptz
poll_count integer NOT NULL DEFAULT 0 CHECK (poll_count >= 0)
poll_interval_seconds smallint NOT NULL DEFAULT 5
  CHECK (poll_interval_seconds BETWEEN 5 AND 30)
```

并用 CHECK/trigger 或条件 SQL 保证：

- `approved` 必须有 `user_id,approved_at`；
- `denied` 必须有 `denied_at`；
- `consumed` 必须有 `user_id,device_id,approved_at,consumed_at`；
- `expires_at > created_at` 且最大 10 分钟；
- key algorithm 与解析后的 SPKI 算法一致由应用验证，数据库保存 fingerprint 复核结果；
- `(tenant_id,user_code_mac)` 与 `device_code_hash` 唯一。

### 9.3 PostgreSQL nonce 表与 RLS

```sql
CREATE TABLE device_proof_nonces (
  id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tenant_id uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
  key_fingerprint bytea NOT NULL CHECK (octet_length(key_fingerprint)=32),
  nonce_hash bytea NOT NULL CHECK (octet_length(nonce_hash)=32),
  credential_kind text NOT NULL
    CHECK (credential_kind IN ('none','device_code','access_token','refresh_token')),
  request_hash bytea NOT NULL CHECK (octet_length(request_hash)=32),
  occurred_at timestamptz NOT NULL DEFAULT transaction_timestamp(),
  expires_at timestamptz NOT NULL,
  CHECK (expires_at = occurred_at + interval '15 minutes'),
  UNIQUE (tenant_id,key_fingerprint,nonce_hash)
);
SELECT app.enable_tenant_rls('device_proof_nonces');
```

`nonce_hash=SHA-256(raw 16-byte nonce)`，`request_hash` 只能用第 4.6 节 `nonce_request_hash`。保留期固定 15 分钟，覆盖 10 分钟 access lifetime 和双向 skew；caller 不得提供或覆盖 `occurred_at/expires_at`。

数据库必须用 `BEFORE INSERT` trigger 把 `NEW.occurred_at=transaction_timestamp()`、`NEW.expires_at=transaction_timestamp()+interval '15 minutes'`；同时 `FORCE ROW LEVEL SECURITY`。`aegis_app` 撤销 base table 的 `INSERT/UPDATE/DELETE/TRUNCATE`，只授予 tenant RLS 下必要的 `SELECT` 与固定 `app.consume_device_proof_nonce(tenant,key_fingerprint,nonce_hash,credential_kind,request_hash)` SECURITY DEFINER 函数 EXECUTE；函数没有时间参数、校验当前 tenant context、固定 `search_path`，owner 不是应用登录角色且撤销 PUBLIC EXECUTE。应用不得拥有 table owner/BYPASSRLS。函数内部用 `INSERT ... ON CONFLICT DO NOTHING RETURNING id` 并返回 `consumed boolean`，不能让 unique violation 把整个 transaction 置 aborted；`consumed=false` 时调用方在同一 transaction 写 `audit_events`/`risk_events` replay 风险行、commit 后返回统一 `401 invalid_proof`。函数调用与第 6.6 节受保护动作同一 transaction。

清理由独立 `aegis_nonce_gc` NOLOGIN/作业身份经固定 SECURITY DEFINER 函数执行；runtime role 不得继承它。清理函数只允许 `DELETE WHERE expires_at <= statement_timestamp()`，参数不能缩短 15 分钟，禁止 UPDATE/TRUNCATE，并记录删除计数。函数 owner 不是应用登录角色，固定 `search_path` 且撤销 PUBLIC EXECUTE。不能用进程内 map 或 fail-open Redis 代替；数据库不可写或 privilege/RLS 校验失败时请求失败，不作可用性降级。

### 9.4 refresh family 与 replay 约束

family 是独立父实体，避免仅靠每个 token 重复字段来“约定”同 session/device/key：

```sql
CREATE TABLE refresh_families (
  tenant_id uuid NOT NULL,
  id uuid NOT NULL,
  session_id uuid NOT NULL,
  user_id uuid NOT NULL,
  device_id uuid NOT NULL,
  key_fingerprint bytea NOT NULL CHECK (octet_length(key_fingerprint)=32),
  status text NOT NULL CHECK (status IN ('active','revoked','compromised','expired')),
  absolute_expires_at timestamptz NOT NULL,
  idle_expires_at timestamptz NOT NULL,
  last_used_at timestamptz,
  PRIMARY KEY (tenant_id,id),
  UNIQUE (tenant_id,id,session_id,user_id,device_id,key_fingerprint),
  FOREIGN KEY (tenant_id,session_id,user_id,device_id)
    REFERENCES sessions(tenant_id,id,user_id,device_id)
);
```

因此 `sessions` 必须先增加 `UNIQUE(tenant_id,id,user_id,device_id)`；client session 的 device 非空。`refresh_tokens` 至少增加/约束：

```sql
family_id uuid NOT NULL,
device_id uuid NOT NULL,
generation integer NOT NULL CHECK (generation >= 0),
parent_id uuid,
key_fingerprint bytea NOT NULL CHECK (octet_length(key_fingerprint)=32),
UNIQUE (tenant_id,id),
UNIQUE (tenant_id,family_id,id),
UNIQUE (tenant_id,family_id,session_id,device_id,id),
UNIQUE (tenant_id,family_id,generation),
FOREIGN KEY (tenant_id,family_id,session_id,user_id,device_id,key_fingerprint)
  REFERENCES refresh_families
    (tenant_id,id,session_id,user_id,device_id,key_fingerprint),
FOREIGN KEY (tenant_id,family_id,session_id,device_id,parent_id)
  REFERENCES refresh_tokens(tenant_id,family_id,session_id,device_id,id),
FOREIGN KEY (tenant_id,family_id,session_id,device_id,replaced_by)
  REFERENCES refresh_tokens(tenant_id,family_id,session_id,device_id,id)
```

并建立 partial unique index：

```sql
CREATE UNIQUE INDEX refresh_tokens_one_active_family
ON refresh_tokens(tenant_id,family_id)
WHERE status='active';
```

`refresh_families` 与 `refresh_tokens` 都启用 FORCE RLS。`parent_id IS NULL` 当且仅当 `generation=0`；`generation>0` 必须 parent 非空。`replaced_by` 只允许 rotated 行非空，并由 deferred constraint trigger 在 commit 时确认它指向同 family 的 `generation+1` 且对方 `parent_id=本行.id`。只用 `(tenant_id,parent_id)` 或 `(tenant_id,replaced_by)` 的 FK 不合格，因为仍允许跨 family 串链。

响应重放表至少包含 tenant、family、old/new token id、session、device、request id、`body_hash`、`replay_request_hash`、key fingerprint、加密响应、key version、created/replay-started/expires，并有：

```sql
UNIQUE (tenant_id,old_token_id,refresh_request_id),
CHECK (replay_started_at >= created_at),
CHECK (expires_at = replay_started_at + interval '30 seconds'),
FOREIGN KEY (tenant_id,family_id,session_id,device_id,old_token_id)
  REFERENCES refresh_tokens(tenant_id,family_id,session_id,device_id,id),
FOREIGN KEY (tenant_id,family_id,session_id,device_id,new_token_id)
  REFERENCES refresh_tokens(tenant_id,family_id,session_id,device_id,id),
FOREIGN KEY (tenant_id,session_id) REFERENCES sessions(tenant_id,id),
FOREIGN KEY (tenant_id,device_id) REFERENCES devices(tenant_id,id)
```

`replay_started_at` 与 `expires_at` 必须由数据库在 commit 前最后一条 INSERT 中设为 `statement_timestamp()` 与 `statement_timestamp()+interval '30 seconds'`，caller 不得传入；commit latency 只会保守缩短客户端可见窗口，不能延长 30 秒。`refresh_request_id` 存 UUID、`body_hash/replay_request_hash/key_fingerprint` 均恰好 32 字节。该表启用 FORCE RLS；runtime role 不得 UPDATE/DELETE/TRUNCATE replay row，只能在 rotation transaction 通过固定函数 INSERT、在 rotated retry transaction 标记受控使用计数。GC 权限与第 9.3 节相同隔离。

### 9.5 access-token jti registry

`client_access_token_jtis` 至少包含 `tenant_id, issuer, jti_hash, session_id, device_id, signing_kid, signing_key_version, issued_at, expires_at, revoked_at`；除 `revoked_at` 外这些列全部 NOT NULL，特别是引用侧 `session_id/device_id` 不得以 NULL 绕过复合 FK。`jti_hash` 恰好 32 字节，`signing_kid` 满足第 18.3 节 kid grammar，`signing_key_version` 是 `1..2147483647` 的整数，并有：

```sql
UNIQUE (tenant_id,issuer,jti_hash),
FOREIGN KEY (tenant_id,session_id,device_id)
  REFERENCES sessions(tenant_id,id,device_id),
CHECK (expires_at > issued_at AND expires_at <= issued_at + interval '10 minutes'),
CHECK (signing_kid ~ '^[A-Za-z][A-Za-z0-9_-]{0,63}$'),
CHECK (signing_key_version BETWEEN 1 AND 2147483647)
```

`sessions` 父表必须先有 `UNIQUE (tenant_id,id,device_id)`；`audience='client'` 的 session 必须要求 device_id NOT NULL（以 CHECK/constraint trigger 强制），不能让复合 FK 因 NULL 跳过。PG18 负测必须分别拒绝 JTI 的 NULL session、NULL device、同 tenant 错配 session/device。表启用 FORCE RLS。签发与 jti INSERT 同事务；runtime role 不得删除。GC 只能删除 `expires_at + interval '120 seconds' <= statement_timestamp()` 的行。logout/device revoke 可设置 `revoked_at`，每请求按第 7.3 节 fail closed 校验。

### 9.6 `device_tokens` 决策

MVP 不把 `device_tokens.kind='refresh'` 作为第二套 refresh authority。session + `refresh_tokens` 是唯一人机 Client session/refresh 源。迁移必须把全部现存 `device_tokens.kind='refresh'` 标记 `revoked`，随后收紧 CHECK 使新行只允许 `kind='config'`；不得把旧 token hash 复制进新 refresh 表，也不得生成伪造 key/family 维持兼容。`kind=config` 只有在第 9.1 节复合 FK 全部验证后可保留；无法证明同租户、同用户、同设备的行同样撤销。

### 9.7 分阶段 migration、backfill、cutover 与 rollback

迁移是 credential boundary，按以下不可跳步序列执行；每阶段生成 tenant/row count、异常主键和约束结果的脱敏报告：

1. **Preflight/冻结写入**：确认落地 migration 编号；枚举第 9.1 节所有列、constraint、索引和仓库外消费者；备份并完成恢复演练；禁止创建新的 `audience=client` api token、`device_tokens.kind=refresh` 和旧式 Client session。发现未知消费者不兼容时停止，不伪造兼容数据。
2. **Expand**：只新增 nullable columns、父表复合 UNIQUE、新 nonce/replay/jti/join tables、trigger/functions/RLS/privileges；新 FK 先 `NOT VALID`。尚未 cutover 的旧服务不得获得新表权限。
3. **分类 backfill**：在快照 transaction 中按 `(tenant_id,id)` 连接并分类 `provable / orphan / cross_tenant / unprovable_key`。只 backfill 可从现存事实逐字节证明的 tenant/user/device/family 字段。不得从默认 tenant 猜测，不得为 legacy row 生成 SPKI、fingerprint、family、parent、jti、user-code MAC 或 replay ciphertext。
4. **显式撤销/隔离**：全部 pending/approved legacy `device_authorizations` 置 expired/denied，用户重新授权；全部现有 client access/session/refresh 与 `api_tokens.audience=client` 撤销，因为旧 token 缺少本契约 issuer/cnf/jti 证明；`device_tokens.kind=refresh` 按第 9.6 节撤销。legacy device 只有在其公钥能严格解析为允许的 SPKI、tenant/user 复合关系成立且 fingerprint 可重算时才保留 active，否则 revoke 并要求重新配对。跨租户/orphan device-scoped subscription credential 撤销；关联不可信的 active config bundle 撤销。绝不生成假 legacy key 来维持登录。
5. **FK/join backfill**：把可证明的 `config_bundles.node_ids` 写入 `config_bundle_nodes` 并做双向 count/set 比较；对 `credential_access_log.config_bundle_id` 的 orphan/cross-tenant 值先导出脱敏异常报告，再置 NULL。完成所有 `NOT VALID` FK 的跨租户负测后 `VALIDATE CONSTRAINT`。
6. **Cutover transaction/maintenance window**：停止旧 writer，运行最终增量 backfill，验证异常计数为零或均已按第 4 步撤销；启用新 Client gateway route、issuer、PoP 和唯一 refresh authority；切换 config bundle 读取到 join table；把 required columns 设 NOT NULL、启用 FORCE RLS 与最终 grants。新 gateway 健康探针必须完成真实签发/PoP/撤销的隔离测试租户流程，不能只看 200。
7. **Contract**：观察至少一个 access TTL + skew（12 分钟）且无旧 writer 后，删除裸 UUID FK/旧索引，停止读取 `node_ids`，再在后续 migration 删除废弃列。任何 credential secret、旧 hash 或撤销记录按既定 retention 保留，不因 schema 清理复活。

rollback 分界明确：第 6 步前可回滚新增对象与 dual-write，同时恢复旧服务，但已按安全判定撤销的 credential **不恢复**；用户重新认证。第 6 步后只允许“关闭 Client 路由 + 回滚应用读路径 + forward-fix migration”，不得恢复旧 issuer、旧 refresh authority、已撤销 token 或移除已验证复合 FK/RLS。若恢复演练、row-set 对账、PG18 constraint validation 或 revoke count 任一失败，cutover 保持 NO-GO。

### 9.8 Device issuance response replay 表

迁移必须新增 `device_issuance_response_replays`。`id uuid PRIMARY KEY`，`tenant_id/authorization_id/device_id/session_id/refresh_family_id/stable_request_hash/key_fingerprint/state/created_at/expires_at/replay_count` 全部 NOT NULL；`stable_request_hash/key_fingerprint` 恰好 32 bytes；`state` 只允许 `prepared|finalized`；`replay_count` 默认 0 且不得小于 0。`response_envelope_ciphertext/response_body_hash/envelope_kid/envelope_key_version/aead_nonce/aead_tag` 在 prepared 行必须全部 NULL，在 finalized 行必须全部 NOT NULL，由同一个 CHECK 强制；finalized 的 body hash 恰好 32 bytes、key version 为 `1..2147483647`、nonce 恰好 12 bytes、tag 恰好 16 bytes。`replayed_at timestamptz(6)` nullable；`created_at/expires_at` 为 `timestamptz(6)` 且 CHECK `expires_at=created_at+interval '30 seconds'`。status、headers 与 body 只存在于 finalized 行的加密 envelope；允许 headers 恰好为 `Cache-Control: no-store`、`Content-Type: application/json`、`X-Request-ID: <首次请求的 request id>`，名称和值都作为精确 UTF-8 bytes 加密保存，禁止重建新的 X-Request-ID。body 是首次响应 exact bytes。

唯一约束为 `UNIQUE(tenant_id,authorization_id,device_id,key_fingerprint,stable_request_hash)`。复合 FK 至少包括 `(tenant_id,authorization_id,device_id) -> device_authorizations(tenant_id,id,device_id)`、`(tenant_id,device_id) -> devices(tenant_id,id)`、`(tenant_id,session_id,device_id) -> sessions(tenant_id,id,device_id)`，以及 `(tenant_id,refresh_family_id,session_id,device_id)` 指向同 tenant/session/device 的 refresh family；父表必须先建立相应复合 UNIQUE。表启用并强制 `FORCE ROW LEVEL SECURITY`。

`created_at` 与 `expires_at` 只由 `app.prepare_device_issuance_replay(...)` SECURITY DEFINER 函数插入 prepared 行时设置为同一个数据库 `statement_timestamp()::timestamptz(6)` 与其加 `interval '30 seconds'`；caller 不得传时间。该函数返回数据库生成的 `id,created_at,expires_at`。gateway 只能用这些返回值构造第 18.3 节 AAD 并完成 AEAD；随后调用 `app.finalize_device_issuance_replay(id,ciphertext,body_hash,kid,version,nonce,tag)`，该函数只允许同 tenant、同 transaction、`state='prepared'` 的行一次性转为 finalized。finalize 调用必须是 commit 前最后一条 SQL；DEFERRABLE INITIALLY DEFERRED constraint trigger 必须在 commit 时拒绝任何 prepared 行，因此 authorization consume、session/token/JTI 不可能在缺少 finalized replay envelope 时提交。重放查询只允许返回 finalized 行。

runtime `aegis_app` 撤销 base table 的 INSERT/UPDATE/DELETE/TRUNCATE，只授予上述 prepare/finalize、tenant RLS 下按稳定键读取 finalized ciphertext 的受限函数，以及“新 nonce 已消费后递增 replay_count/设置 replayed_at”的固定函数 EXECUTE；函数 owner 不得是应用角色，固定 search_path 且撤销 PUBLIC。独立 GC role 只能删除 `expires_at + interval '120 seconds' <= statement_timestamp()` 的 finalized 行；prepared 行只能由事务回滚消失。RLS、FK、unique、ACL、DB clock、30 秒/120 秒边界、并发首次 prepare/finalize、finalize 失败回滚与 GC 都必须在真实 PG18 负测通过，否则 NO-GO。

## 10. human code、限流与审计脱敏

### 10.1 code 生成和存储

- device code：32 随机字节，base64url no padding；数据库只存 SHA-256。
- human user code alphabet 精确为 31 个 ASCII 字符 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`（排除 `0/O/1/I/L`）；不能把它误称为 32 字符 alphabet。生成 8 字符，显示 `XXXX-XXXX`。
- 均匀采样：逐个读取 CSPRNG byte；只接受 `<248` 的 byte，索引为 `byte % 31`，其余 rejection-sample。不得用随机 byte 直接 `%31`。
- normalize 只接受正则 `^[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}-[23456789ABCDEFGHJKMNPQRSTUVWXYZ]{4}$` 或同 alphabet 的 8 字符无连字符形式；ASCII 小写可先转大写。除此之外的 whitespace、Unicode、多个/错位连字符或标点直接拒绝。normalized code 是移除唯一显示连字符后的 8 ASCII bytes。
- tenant UUID bytes 是 RFC 9562/network order 的 16 raw bytes，按 canonical UUID 的十六进制从左到右解码；不是 36 字符文本、数据库本机 endian 或 UTF-16。数据库只存 `HMAC-SHA-256(pepper, tenant_uuid_16_bytes || 0x00 || normalized_code_8_ASCII_bytes)`。
- `AEGIS_DEVICE_USER_CODE_PEPPER` 是独立至少 32 字节 secret；不得复用 JWT secret、MasterKey 或 config signing seed。缺失时 Client/Public 网关拒绝启动相关路由。

机器可验证 human-code 向量（测试 pepper，不是生产 secret）：

```json
{
  "vector_id": "human-code-v1-01",
  "alphabet_ascii": "23456789ABCDEFGHJKMNPQRSTUVWXYZ",
  "alphabet_length": 31,
  "display_code": "2A3B-4C5D",
  "normalized_code_ascii": "2A3B4C5D",
  "tenant_uuid": "00112233-4455-6677-8899-aabbccddeeff",
  "tenant_uuid_bytes_hex": "00112233445566778899aabbccddeeff",
  "separator_hex": "00",
  "pepper_hex": "000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f",
  "hmac_sha256_b64u": "MPIQP9e8MhaLGtjekyvuDqaGZDD392R4-gzs3vzfBdc"
}
```

### 10.2 冻结限流

创建 authorization：

- 每 IP：10 次 / 10 分钟；
- 每 IPv4 /24 或 IPv6 /48：100 次 / 10 分钟；
- 每 key fingerprint：5 次 / 24 小时；
- 每租户全局硬上限由配置给出，默认 10,000 次 / 小时。

human code lookup/approve/deny：

- 每账户：10 次 / 分钟、50 次 / 小时；
- 每 IP：20 次 / 分钟；
- 每 code MAC：5 次失败后将 authorization 置 denied/locked 风险状态，不提示是否命中。

Device Code poll：遵守每 authorization 5..30 秒 interval，并叠加 IP/net/key 维度。强制限制必须以 PostgreSQL 状态/条件更新保证；Redis 只能做提前削峰，Redis 故障不能放开 DB 硬上限。429 的 `Retry-After` 必须反映 authorization 当前 interval，不能沿用全局固定 60 秒。

### 10.3 审计

审计动作至少包括：authorization.create/lookup/approve/deny/expire/consume、device.register/revoke、session.create/revoke、refresh.rotate/replay/reuse_compromise、proof.replay。

允许记录 tenant、authorization/device/session UUID、algorithm、结果、request id、actor、IP hash、UA 摘要和内部原因码。禁止记录：

- 明文或 hash/MAC 形式的 user code/device code；
- access/refresh token、`ath`、PoP signature；
- 完整 SPKI、公钥或完整 fingerprint；日志最多使用不可逆审计别名或 8 字节显示前缀；
- refresh replay ciphertext 的明文。

对外错误统一，不得通过状态码、耗时或文案区分“code 不存在”和“code 存在但属于其他租户/用户”。

## 11. Kotlin/Compose 与 Rust Core 边界

### 11.1 Kotlin/Android 所有权

- Compose 页面、浏览器/fragment 导入、生命周期、网络/权限 UI；
- AndroidKeyStore P-256 key 生成、用户认证策略和不可导出 `KeyHandle`；
- `Signature` provider 调用，DER 严格解析到 P1363 low-S 的平台适配；
- encrypted secure-store adapter 和 key invalidation 事件；
- HTTP transport 只能发送 Rust 给出的最终 body bytes/headers，不得重建 JSON。

Kotlin 对 Rust 只暴露：

```text
KeyHandle.id()
KeyHandle.algorithm()
KeyHandle.public_spki_der()
KeyHandle.sign(canonical_bytes) -> signature_bytes
SecureStore.get/set/delete(opaque_key, bytes)
```

private key 永不跨 FFI，Compose state、SavedStateHandle、日志和崩溃报告永不保存 refresh token 或完整签名材料。

### 11.2 Rust Core 所有权

- API DTO、Device Code 状态机、expiry/poll/backoff/cancellation；
- 最终 JSON bytes 序列化、PoP V1 canonicalizer、body hash/ath/nonce/header；
- key algorithm capability 选择，但实际签名通过 Kotlin `KeyHandle`；
- token set 的内存生命周期与 secure-store opaque handle；
- config/update 签名验证、错误归一化、跨平台黄金向量测试。

Rust 返回 UI 的状态只包含 `authorization_pending/approved/denied/expired/slow_down/error` 和安全展示数据，不返回 refresh secret。Android 默认 signer 是 Kotlin KeyHandle；桌面实现相同接口，可在 OS 安全存储支持下使用 Ed25519。

### 11.3 稳定 FFI DTO

至少冻结：`Capabilities`、`StartAuthorizationRequest/Response`、`PollState`、`TokenMetadata`、`ClientAuthError`。DTO 带显式 schema version；不得让 Kotlin 直接依赖代理内核内部类型，也不得让 Rust 假设 Android 私钥可导出。

## 12. 订阅与设备绑定

Client 读取订阅/config 时必须把当前 principal device id 传入订阅认证：

- `scope='subscription'` 可按产品策略使用；
- `scope='device'` 必须满足 `credential.device_id = principal.did` 且 device/session active；
- 设备撤销必须调用单一 SECURITY DEFINER 数据库函数；它先以 `SELECT 1 FROM devices WHERE tenant_id=$1 AND id=$2 AND user_id=$3 FOR UPDATE` 取得该 device 的排他行锁，再在同一事务内原子完成完整集合：撤销 device；撤销该 device 的全部 client sessions、refresh families 及 refresh tokens；设置全部未过清理期 JTI registry 行 `revoked_at`；撤销全部 device-scoped subscription credentials；撤销保留的 `device_tokens.kind='config'`；把该 device 的未过期 config bundles 标记 revoked/不可服务。issuance/refresh replay 证据保留到原 retention，但任何 replay 在返回 bytes 前仍须重新校验 device/session/family/JTI 均 active，因此不能复活凭据。所有可能创建或重新激活上述 credential、config bundle、client session、refresh family/refresh token、JTI 或 config device token 的 SECURITY DEFINER 写函数，必须先用完全相同的 `(tenant_id,device_id,user_id)` 键和 `FOR UPDATE` 锁定 device，取得锁后重新断言 `status='active'`，才可写子行；runtime role 撤销这些基表的 INSERT/UPDATE/DELETE/TRUNCATE。这样创建先提交时后到的 revoke 会撤销新子行，revoke 先提交时后到的创建会在重检状态时失败。deferred constraint trigger 只作 commit 时的第二道不变量检查，不代替并发序列化；函数、锁、状态重检或 trigger 任一失败则事务整体回滚；
- wrong/no device、跨租户、过期、grace/revoked 状态采用统一不可探测响应。

现有 `internal/domain/subscription/service.go` 没有完成此检查，因此 CLIENT-AUTH-01 即使能签发 token，也不能在修复前标记为集成完成。

## 13. 测试与故障矩阵

### 13.1 黄金向量和算法

- Go/Rust/Kotlin 从同一 JSON 读取 canonical/body/ath/SPKI/固定签名向量；canonical/hash/encoding 逐字节一致。固定签名三方都必须验签成功，但运行时重新生成的 P-256 签名不要求与向量字节相等。
- P-256：合法 P1363 low-S 做数学验签；拒绝 DER、high-S、错误曲线、非最小 DER 输入转换、r/s 为 0 或越界；另测两个不同但合法的 low-S signature 都能验证同一 message。
- Ed25519：合法 raw 64 字节；拒绝 prehash 替代、长度错误、弱/畸形 SPKI。
- CRLF、末尾 LF 缺失、origin 大小写、默认端口、escaped path、RawQuery 顺序、body 空白、Content-Encoding 全部有负向量。
- 解析本文件全部 JSON code block；重算 canonical/body/ath、nonce request、refresh replay request、issuance stable request、JWT HS256、AAD AES-256-GCM ciphertext/tag 与 human-code HMAC，必须匹配。

### 13.2 状态与并发

- pending→approve→single consume；deny、expire 边界；approve/deny/consume 三方竞态。
- 两个 poller、过快轮询、interval 增长、事务提交后 HTTP 响应丢失。
- Device Code consume commit 后响应丢失：同 body/device/key + 新 nonce 命中 issuance replay 并返回完全相同 status、三项 headers（含首次 `X-Request-ID`）和 body；不同稳定字段、旧 nonce、过窗、ciphertext/tag/hash 错误均 fail closed 且不再签发。
- duplicate start、同 key 多 authorization、device limit 在 consume 时竞争。
- 重装/换钥不覆盖 active key；revoke 后所有 session 立即无效。

### 13.3 PoP 与 token

- wrong key/key id/cnf/alg；method/path/query/body/ath 篡改；旧/未来 timestamp。
- Authorization 缺失/重复/逗号合并、`Bearer`、scheme 大小写变化、双空格/HTAB/尾随空白，以及把 scheme/SP 错算进 ath。
- 同 tenant/key/nonce replay、跨租户 replay、nonce DB insert 故障、RLS 无上下文。
- claim 缺失、aud/kind/did/sid/tid/sub 不一致、unknown scope、重复 jti、过期 access。
- unknown/missing SNI、Host 不匹配、forwarded header 注入、同 SNI 多 tenant 启动失败；匿名请求的 route tenant/origin/issuer 必须一致。
- 每请求 session/device/cnf/scp 校验；DB/Redis/cache 故障组合。
- 有效 PoP 后的 pending/slow_down/forbidden/conflict/compromise 响应都确认 nonce 与对应 poll/risk/revoke 已 commit；注入 commit failure 时不得泄漏原 typed outcome。

### 13.4 refresh

- 成功原子 rotate；两个并发 refresh 只有一个 generation 新增。
- commit 前故障回滚后 old token 仍 active。
- commit 后响应丢失，30 秒内相同 request id/body/device + 新 nonce 返回逐字节相同响应。
- request id/body/device/key 不同、旧 nonce、超过 30 秒都触发 family compromise。
- 验证 retry 的 `nonce_request_hash` 因新 nonce 不同、`replay_request_hash` 保持相同；交换两个 hash 列必须失败。
- replay ciphertext 解密失败 fail closed 并撤销/告警；不得重新生成“近似相同”响应。
- absolute/idle expiry、logout/device revoke 与 refresh race。

### 13.5 tenant/RLS/约束

- 使用真实 `aegis_app` PG18：无 tenant context 看不到行；A 不能查询/批准/消费/撤销 B。
- 每个复合 FK 有跨 tenant INSERT/UPDATE 拒绝测试。
- nonce unique 在并发事务中只允许一个成功；DB 不可用请求不放行。
- runtime role 不能 UPDATE/DELETE/TRUNCATE nonce/replay/jti；GC 不能提前删除；15 分钟/30 秒/`exp+120s` 边界用数据库时钟验证。
- refresh family 只有一个 active；generation 唯一；parent/replaced_by、replay old/new 不能跨 tenant/family。
- 第 9.1 节每一条 retained FK 都有跨 tenant INSERT/UPDATE 拒绝测试；`node_ids` 与 join table cutover 前做 set equality。
- 直接 INSERT/UPDATE 制造错 user 的 subscription credential/config bundle 必须由三元复合 FK 拒绝；device revoke 与并发 credential/session/family/token/config-bundle 创建或重新激活竞态必须由第 12 节规定的所有写函数同键 `FOR UPDATE`、锁后状态重检和 deferred constraint trigger 保证 commit 后没有 active 子对象。真实 PG18 双连接 barrier 测试必须覆盖“创建先拿锁”和“撤销先拿锁”两个提交顺序。
- issuance replay 的 unique/FK/FORCE RLS/最小函数 ACL、30 秒 DB clock TTL、120 秒 GC grace、并发 retry 和 runtime base-table 写删改禁止必须在真实 PG18 通过。

### 13.6 Android/Rust 故障

- AndroidKeyStore 不可用、key invalidated、设备锁定、provider 返回异常 DER/high-S。
- app 被杀/后台/弱网/时钟偏差；authorization 恢复不泄露 secret。
- FFI cancellation、Rust panic、secure-store 损坏、JNI byte array 被重建或截断。
- 日志、analytics、Compose state、崩溃报告扫描不到 code/token/private key/signature。

## 18. CLIENT-AUTH-07 补充冻结（设计，不是实现）

### 18.1 Device Code issuance response replay

Device Code consume 的成功路径与 refresh replay 采用相同的“先持久化、后响应”规则。授权已 approved、Device Code 与 PoP 已验证后，消费事务必须在把 authorization 标记为 consumed 的同一事务内：签发 session/refresh/access，最终序列化 response status、允许 headers（恰好 `Cache-Control`、`Content-Type`、首次请求 `X-Request-ID`）与 exact body；调用第 9.8 节 prepare 函数取得数据库生成的 replay id/created/expires；用该精确 expiry 构造 AAD 并以 server envelope AEAD 加密完整 response envelope；再以 finalize 函数一次性保存 ciphertext/tag/hash/key metadata 并把行转为 finalized。finalize 是 commit 前最后一条 SQL，deferred trigger 禁止 prepared 行提交。只有 commit 成功后才可发送这些已冻结 bytes。

replay 的稳定查询键为 `tenant_id + authorization_id + device_id + key_fingerprint + stable_request_hash`；它**不得**依赖客户端从未收到的 response body 或 response hash，也没有额外的 canonical request id。`stable_request_hash=SHA-256(stable_record_bytes)`；`stable_record_bytes` 以 ASCII `AEGIS-DEVICE-ISSUANCE-REPLAY-V1` 加单个 NUL 开头，随后严格按 `origin, method, target, request_body_sha256_b64u, device_code_ath_b64u, key_fingerprint_b64u` 顺序编码。每个字段先转为 UTF-8（后三个 b64u 字段是 canonical ASCII），再写无符号 32-bit big-endian byte length 和字段 bytes；禁止缺字段、额外字段、文本分隔符、Unicode normalize、timestamp、nonce 或 signature。response-body SHA-256 仅保存于 replay row，并在 AEAD 解密后用于完整性验证。重试必须使用**新 nonce**、同一 device、同一 exact request body、同一 key 和同一 stable record；在数据库时钟计算的 30 秒窗口内，服务端解密并返回原有 status、headers 与 body，逐字节相同，不新增 session/token/jti，也不再次 consume。已 consumed 的任意其他请求均 fail closed；不得重新进入普通轮询、重新签发或返回近似响应。

加密明文 envelope 固定为 LF 文本：域标签 `AEGIS-DEVICE-ISSUANCE-RESPONSE-V1`，随后依次为 `status:200`、`header-count:3`、按 ASCII 名称排序的三行 `header:<Name>:<exact value>`、十进制 `body-length:<byte count>`、`body-b64u:<exact body bytes>`，每行及末行均有 LF。禁止 JSON map 重序列化、自动生成新的 request id、额外 header 或换行转换；解密后同时校验 status/header allowlist、body length 和 response body SHA-256。

故障注入必须覆盖：commit 前失败后 authorization 仍可按正常首次请求消费；commit 成功但响应丢失后合格重试返回原 response；replay row/AEAD 写入失败时整个 issuance 回滚且不发送成功响应；ciphertext/key 不可解密、unknown key version、DB/RLS 故障均不消费或恢复 credential，并记录受控风险事件。上述任一测试失败为 release NO-GO。

### 18.2 Credential ownership and config-bundle coherence

`subscription_credentials` 的存活所有权必须由数据库可证明的复合键同时锁定：

- `(tenant_id, subscription_id, user_id) -> subscriptions(tenant_id,id,user_id)`；
- nullable `(tenant_id, device_id, user_id) -> devices(tenant_id,id,user_id)`；
- 直接 `(tenant_id,user_id) -> users(tenant_id,id)` 是冗余存在性 FK，**不是必需项**：subscription 三元 FK 在 device 为 NULL 时仍证明 user，device 三元 FK 在非 NULL 时再证明同一 user；若为兼容现有 schema 保留直接 FK，它也不能替代前两条同一性 FK。

前两项 subscription/device 三元同一性 FK 不是可选的 application join；直接 users 存在性 FK 是冗余可选项。父表须有对应 `(tenant_id,id,user_id)` UNIQUE，所有实际采用的 FK 必须在迁移 backfill/negative tests 后 VALIDATE。认证时 principal 的 `tid/sub/did` 必须与 credential 的 tenant、subscription、user 及 device scope 一致；`scope='device'` 还要求非空 `device_id=principal.did`。

为避免 PostgreSQL `MATCH SIMPLE` 在 device_id NULL 时跳过整条复合 FK，迁移必须在 `subscription_credentials` 与 `config_bundles` 同时新增 non-NULL STORED generated column：`device_binding_key text GENERATED ALWAYS AS (CASE WHEN device_id IS NULL THEN 'subscription' ELSE 'device/'||device_id::text END) STORED`。credential 父表建立 `UNIQUE (tenant_id,id,subscription_id,user_id)` 和 `UNIQUE (tenant_id,id,subscription_id,user_id,device_binding_key)`；bundle 同时建立始终生效的四列 FK `(tenant_id,credential_id,subscription_id,user_id)`，以及五列 FK `(tenant_id,credential_id,subscription_id,user_id,device_binding_key)`。bundle 另以 nullable `(tenant_id,device_id,user_id)` FK 指向 devices。迁移给 bundle 增加 `revoked_at`，并以 CHECK 强制 `revoked_at IS NULL -> credential_id IS NOT NULL`；只有 `revoked_at IS NULL AND expires_at>statement_timestamp()` 的 bundle 可服务。这样 active bundle 的 credential_id 非空，两条 FK 都不会被 NULL 跳过，device binding 又必然同为 subscription scope 或同一 UUID。禁止同用户 device A credential 与 device B bundle 拼接；gateway 只作同一 DB 事实的二次校验。PG18 负测必须证明错 user、同用户错 device、credential NULL 的 active bundle、subscription NULL/NULL 正向、subscription NULL/non-NULL 反向组合在 INSERT 和 UPDATE 时得到预期数据库结果（同样覆盖跨 tenant、错 subscription、删除/撤销 device、bundle 指向其他 credential）；任一失败为 NO-GO，且不得从 UUID 或 URL 推导 tenant。

### 18.3 Versioned keyrings and envelope contract

JWT signing keyring 与 replay/issuance envelope keyring 是不同用途、不同配置名、不同 root secret 的 versioned keyrings。每个条目含不可复用 `kid`、version、状态 `active|verify-only|retired`、创建时间和明确用途；恰有一个 active signing key 与恰有一个 active AEAD encryption key。验证/解密可接受 active 或仍在保留期内的 verify-only key；unknown kid/version、retired key、用途不符、重复 kid、零或多个 active、缺失材料、配置热更新或重启后 keyring 不一致，均 fail closed 并拒绝启动 Client 路由。

JWT header 的 `kid` 选择签名 key；issuer/audience/claims 仍按既有固定规则验证，禁止 key fallback。每个 encrypted replay row 保存 envelope key version/kid、nonce、ciphertext 和认证 tag；AEAD AAD 至少绑定 protocol label、tenant、replay kind、row identity、stable request hash、device/key fingerprint 与 expiry，防止跨 tenant、跨 kind 或跨 row ciphertext 置换。轮换先发布新的 active、把旧 key 置 verify-only，保留至少所有未过期 access token、issuance replay 与 refresh replay 的最长 retention 加时钟偏差后才可 retired/销毁；重启演练必须证明旧 verify-only JWT/replay 仍可验证/解密、新签发只用 active key。unknown 或不可解密记录绝不以重新签发补救。

具体配置冻结如下：`AEGIS_CLIENT_JWT_KEYRING_JSON` 是 UTF-8 JSON array，条目精确为 `{kid,version,status,alg,purpose,created_at,activated_at,verify_only_since,retired_at,secret_b64u}`；只允许 `alg=HS256`、`purpose=client-jwt-signing`，secret canonical base64url 解码后恰好 32 bytes。`AEGIS_CLIENT_REPLAY_AEAD_KEYRING_JSON` 条目精确为 `{kid,version,status,alg,purpose,created_at,activated_at,verify_only_since,retired_at,key_b64u}`；只允许 `alg=A256GCM`、`purpose=client-replay-envelope`，key 解码后恰好 32 bytes。时间字段是固定六位小数 UTC RFC3339 或 JSON null，并满足：active 为非空 `activated_at`、`created_at<=activated_at` 且后两项 NULL；verify-only 为 `created_at<=activated_at<verify_only_since`、`retired_at=NULL`；retired 为 `created_at<=activated_at<verify_only_since<retired_at`。因此创建与激活允许同一瞬间，之后两个状态转换必须严格向后；状态只能单向 `active -> verify-only -> retired`，配置变更不得改写已非 NULL 的生命周期时间。`kid` 统一为 ASCII `^[A-Za-z][A-Za-z0-9_-]{0,63}$`，禁止冒号；version 是 JSON integer 且范围 `1..2147483647`。两个 array 分别按 version 升序加载，拒绝重复 kid 或 version、未知/缺失字段、非 canonical base64url、材料长度错误、created_at/activated_at 非递增、不是恰一 active 或 active/verify-only 的 version 逆序。除 kid 不得跨 ring 复用外，两 ring 内及跨 ring 的 decoded 32-byte key material 也必须逐项互不相等。JWT 签发选择 JWT ring 的唯一 active；JWT 验证只按 header kid 精确选择 active/verify-only 条目。replay/issuance 加密选择 AEAD ring 的唯一 active；解密只按 row 保存的 kid/version 精确选择 active/verify-only 条目。AES-256-GCM nonce 由 CSPRNG 每行生成且恰好 12 bytes，nonce 不得由 request、row id 或时间派生。

AEAD AAD 是下列 UTF-8 字节（每行 LF 结尾，禁止 CRLF/BOM/trim），而非结构化对象的任意序列化：

```text
AEGIS-CLIENT-REPLAY-AAD-V1
kind:<issuance|refresh>
tenant-id:<canonical UUID>
replay-id:<canonical UUID>
stable-request-hash:<base64url SHA-256>
key-fingerprint:<base64url SHA-256 SPKI fingerprint>
expires-at:<UTC RFC3339 microseconds>
```

启动时必须解析两项配置、验证 active 选择、执行固定 JWT HS256 sign/verify 与 AES-GCM seal/open self-test，并检查任何 kid 和任何 decoded key material 都不跨 ring 复用；任一失败使 Client gateway 拒绝启动。每个实例必须计算不可配置的 `keyring_epoch_b64u=base64url(SHA-256(ASCII("AEGIS-CLIENT-KEYRING-EPOCH-V1") || 0x00 || exact AEGIS_CLIENT_JWT_KEYRING_JSON UTF-8 bytes || 0x00 || exact AEGIS_CLIENT_REPLAY_AEAD_KEYRING_JSON UTF-8 bytes))`。两项 JSON 的 exact bytes 由部署 secret 文件提供，禁止解析后重序列化再求摘要。内部 loopback-only `/readyz/client-keyring` 只返回 `{ready:true,keyring_epoch_b64u:<43 ASCII chars>}`，绝不返回 kid 或 key material；普通 `/readyz` 只有在本地自检、数据库 live-reference preflight 与该 epoch 装载完成后才成功。

Client keyring 不支持进程内热更新。轮换控制器必须：先从 ingress 摘除全部 Client 流量并停止新请求；等待所有实例在途签发/加密事务为零；停止全部实例；原子安装一份 exact 双 keyring secret 文件；由控制器独立按上式计算 expected epoch；重启全部实例；逐实例从独立 loopback 地址读取 `/readyz/client-keyring`，要求实例数与部署清单相等、每个 HTTP 200 且 epoch 逐字节等于 expected；再把 `{deployment_id,expected_epoch,instance_ids,verified_at}` 写入追加式部署证据并恢复流量。少一个实例、重复 instance id、任意 epoch 不同或验证期间实例重启都保持 ingress 关闭并回滚配置/进程，不允许混合 epoch 服务流量。该流程的双实例错配故障测试必须证明两个实例各自本地自检成功时，控制器仍因 epoch 不同拒绝恢复 ingress。

JWT verify-only key 的最早 retirement 是以下两者最大值：`verify_only_since + AEGIS_CLIENT_ACCESS_TOKEN_TTL + 120s`，以及数据库中引用其 kid/version 的 JTI `max(expires_at)+120s`；无 JTI 引用时只使用前者。AEAD verify-only key 的最早 retirement 是以下两者最大值：`verify_only_since + max(issuance_replay_ttl,refresh_replay_ttl)+120s`，以及数据库中引用其 kid/version 的 issuance/refresh replay `max(expires_at)+120s`；无 replay 引用时只使用前者。所有时间都来自已持久化的配置生命周期字段或数据库行，不存在进程内 `last_signed_at/rotation_started_at`。每次启动与轮换先查询未过清理门的 JTI/replay distinct kid/version，缺失 active/verify-only key 即拒绝启动/轮换；这就是持久化 key-use manifest，禁止仅凭进程内状态猜测。retired material 不再验证/解密。轮换、重启、删除仍被引用 key、unknown kid/version、错误 nonce/tag/AAD、跨 ring 相同 decoded material、epoch 混合与保留期边界均为强制故障测试和 NO-GO 门。
