# CLIENT-AUTH-01 R1 刷新响应重放附录

状态：FROZEN ADDENDUM / REFERENCE ONLY  
日期：2026-07-30  
基础契约：`docs/潘多拉面板-CLIENT-AUTH-01冻结契约-20260730.md`  
基础契约 SHA-256：`4FC9582DE7121A50FCFF6D65D7C96ACBDF9BDBD4E9C40AD8BFC8F43919B3608E`

本附录只关闭 refresh response replay 的数据库时间与 AEAD AAD 时序歧义。它明确替换三处基础契约规则：§8.2 步骤 3–6 的内部排序、§8.3 第 498 行和 §9.4 第 675 行中“replay INSERT 是 commit 前最后一条 SQL”的时序规则。R1 下，PoP 验证与 nonce 消费仍先于任何 rotation prepare；§8.2 步骤 3–6 仅重排为“应用预生成 secrets/JTI -> 消费 nonce -> prepare 持久化并返回数据库时间 -> 应用构造 exact JWT/响应/AAD/AEAD -> 写成功 audit/risk -> finalize”；最后一条应用 SQL 是 finalize UPDATE。原有原子性、hash-only DB、匹配键、30 秒窗口、compromise、逐字节响应、数据库时钟、commit 后才发送和其余安全语义不变；除本文明确替换的规则外，基础契约全部继续生效。本文不证明数据库、HTTP 路由、生产 keyring 或客户端已经实现，不授权生成或部署任何 secret。

## 1. 决议

基础契约第 9.4 节要求 refresh replay 的 `replay_started_at` 和 `expires_at` 由 commit 前最后一条 INSERT 的数据库 `statement_timestamp()` 生成；第 18.3 节又要求应用在写入 encrypted envelope 前，以该行的精确 `expires_at` 构造 AEAD AAD。应用无法在 INSERT 执行前知道该 INSERT 自身的数据库时间，也不能在一条未返回的 SQL 中间完成应用侧 AEAD。

现冻结方案 R1：refresh rotation 与 issuance 一样使用同一数据库事务内的 `prepare -> 应用 AEAD -> finalize -> commit`。prepare 由数据库生成 row id、`replay_started_at` 和 `expires_at` 并返回；应用用这些精确返回值构造 AAD 和 envelope；finalize 只能在同一事务把 prepared 行一次性变为 finalized，并且必须是 commit 前最后一条应用 SQL。deferred constraint trigger 在 commit 时拒绝任何仍为 prepared 的行。

不允许以下替代方案：

- 应用时间或 caller 传入的时间；
- 先执行独立 `SELECT statement_timestamp()` 再把结果传回 INSERT；
- trigger 覆盖 caller time；
- 从 row id、request、nonce 或时间派生 AEAD nonce；
- 从 AAD 删除 expiry、使用近似 expiry，或在失败后重新签发响应；
- 把明文 token、response body 或 key material交给数据库加密。

30 秒窗口从 prepare 的数据库时间开始。应用加密和 finalize 的耗时只会保守缩短客户端可见窗口，不得延长窗口。

## 2. `client_refresh_response_replays` 状态约束

基础契约 §8.2 步骤 3–6 的内部排序，以及 §8.3 第 498 行与 §9.4 第 675 行的“commit 前最后一条 INSERT/SQL”规则，由本节同时替换。§8.2 的 PoP/nonce 先验、事务原子性、hash-only DB、逐字节响应和 commit 后发送规则不变。表必须新增或冻结以下字段：

```text
id uuid PRIMARY KEY
tenant_id uuid NOT NULL
family_id uuid NOT NULL
old_token_id uuid NOT NULL
new_token_id uuid NOT NULL
session_id uuid NOT NULL
device_id uuid NOT NULL
refresh_request_id uuid NOT NULL
body_hash bytea NOT NULL, length = 32
replay_request_hash bytea NOT NULL, length = 32
key_fingerprint bytea NOT NULL, length = 32
state text NOT NULL, one of prepared|finalized
prepared_xid xid8 NOT NULL
response_envelope_ciphertext bytea NULL
response_body_hash bytea NULL
envelope_kid text NULL
envelope_key_version integer NULL
aead_nonce bytea NULL
aead_tag bytea NULL
created_at timestamptz(6) NOT NULL
replay_started_at timestamptz(6) NOT NULL
expires_at timestamptz(6) NOT NULL
replay_count bigint NOT NULL DEFAULT 0, replay_count >= 0
replayed_at timestamptz(6) NULL
```

必须由一个 CHECK 强制 envelope 六列为同组状态：

- `state='prepared'`：`response_envelope_ciphertext`、`response_body_hash`、`envelope_kid`、`envelope_key_version`、`aead_nonce`、`aead_tag` 全部为 NULL；
- `state='finalized'`：上述六列全部 NOT NULL，且 body hash 恰好 32 bytes、kid 满足 `^[A-Za-z][A-Za-z0-9_-]{0,63}$`、version 为 `1..2147483647`、nonce 恰好 12 bytes、tag 恰好 16 bytes。

仍必须满足：

```text
UNIQUE (tenant_id, old_token_id, refresh_request_id)
CHECK (created_at = replay_started_at)
CHECK (expires_at = replay_started_at + interval '30 seconds')
```

old/new token、family、session、device 的 tenant-scoped 复合 FK、FORCE RLS、owner、ACL、runtime base DML 禁止和 GC 隔离继续按基础契约执行。prepared 行不得被 GC；持久存在 prepared 行视为 invariant 破坏并 fail closed。

## 3. prepare/finalize 函数边界

迁移必须以明确的 `SECURITY DEFINER` 函数提供 refresh rotation。函数 owner 不得是 runtime role；固定 `search_path=pg_catalog`；撤销 PUBLIC；runtime 只获得精确签名的 EXECUTE。

规范函数面为：

```text
app.prepare_client_refresh_rotation(
  p_tenant uuid,
  p_user uuid,
  p_device uuid,
  p_session uuid,
  p_family uuid,
  p_old_token uuid,
  p_refresh_request_id uuid,
  p_body_hash bytea,
  p_replay_request_hash bytea,
  p_key_fingerprint bytea,
  p_new_token uuid,
  p_new_token_hash bytea,
  p_new_jti_hash bytea,
  p_issuer text,
  p_signing_kid text,
  p_signing_version integer
) RETURNS TABLE(
  replay_id uuid,
  new_generation integer,
  access_iat_unix bigint,
  access_exp_unix bigint,
  jti_issued_at timestamptz,
  jti_expires_at timestamptz,
  new_refresh_expires_at timestamptz,
  created_at timestamptz,
  replay_started_at timestamptz,
  expires_at timestamptz
)

app.finalize_client_refresh_replay(
  p_tenant uuid,
  p_replay_id uuid,
  p_response_envelope_ciphertext bytea,
  p_response_body_hash bytea,
  p_envelope_kid text,
  p_envelope_key_version integer,
  p_aead_nonce bytea,
  p_aead_tag bytea
) RETURNS void
```

应用可在事务开始后预生成新 refresh secret、JTI 和所需 CSPRNG 随机量，但不得据此构造时间 claims、写数据库或向客户端发送响应。随后必须先严格验证 PoP，再通过不会把事务置为 aborted 的单条数据库操作原子消费 nonce（例如 `INSERT ... ON CONFLICT DO NOTHING RETURNING`）。只有明确返回 `consumed=true` 才能调用 prepare；若 `consumed=false`，不得调用 prepare、不得创建 generation+1/JTI/replay 或改变 old token/family，只能在同一事务写基础契约要求的脱敏 nonce-replay risk/audit 后提交失败 outcome。

nonce 成功消费后，prepare 必须在同一事务内按全局顺序锁 active device、session、refresh family、old refresh token，重新验证 tenant/user/device/key、状态和数据库 expiry。函数只调用一次 `statement_timestamp()::timestamptz(6)` 并保存为 `v_db_now`；`access_iat_unix=floor(extract(epoch FROM v_db_now))`、`access_exp_unix=access_iat_unix+600`，JTI registry 的 issued/expires 精确为 `to_timestamp(access_iat_unix)` 与 `to_timestamp(access_exp_unix)`。新 refresh token 的 `new_refresh_expires_at` 精确为 `least(family_absolute_expires_at, v_db_now + interval '7 days')`，不得晚于 family absolute expiry；caller 不得传 access/JTI/refresh issued/expires 时间。

prepare 使用上述数据库时间创建 generation+1 token 与预生成的 JTI hash；把 old token 原子改为 rotated 并设置 `replaced_by`；更新 family idle/last-used；最后插入 prepared replay。该 INSERT 以同一个 `v_db_now` 同时设置 `created_at` 与 `replay_started_at`，设置 `expires_at=v_db_now+interval '30 seconds'`、`prepared_xid=pg_current_xact_id()`，并返回全部精确时间。应用只能使用返回的 `access_iat_unix/access_exp_unix` 构造 JWT claims。响应整数 `refresh_expires_in` 必须严格计算为 `greatest(0, least(2592000, floor(extract(epoch FROM new_refresh_expires_at))::bigint - access_iat_unix))`；起点只允许同一 prepare 返回的 `access_iat_unix`，expiry 只允许同一 prepare 返回的、已按 absolute/idle 取最小值的 `new_refresh_expires_at`，不得使用应用时钟、ceil、round 或重新读取/重算时间。若 DB 计算的任一时间与 family absolute/idle/session/device 状态不相容，prepare 在写入前 fail closed。

finalize 必须同时满足 tenant、row id、`state='prepared'` 和 `prepared_xid=pg_current_xact_id()`；只能一次 UPDATE 成 finalized。不同事务、二次 finalize、错误 tenant、过期或字段长度/grammar 不合格全部拒绝。成功路径的唯一顺序固定为 `应用预生成 secrets/JTI -> 验证 PoP -> 原子消费 nonce 且确认 consumed=true -> prepare -> 应用构造 exact JWT/响应/AAD/AEAD -> 同事务写 required refresh.rotate success audit/risk facts -> finalize -> COMMIT -> 发送响应`；nonce 在 prepare 之前消费，prepare 后不得再次写 nonce。finalize 成功后不得再执行其他应用 SQL。

finalize 或 commit 失败时，上述 audit/risk、rotation、token、JTI、family 和 replay 同时回滚且不能发送成功响应。事务失败后的基础设施故障证据只能由事务外受限通道追加一条不含 token、ath、完整 fingerprint、plaintext/ciphertext 或 key material 的失败事件；该事件不得伪称 rotation 已提交，也不得恢复或重新签发 credential。

deferred constraint trigger 必须在 commit 时按主键重新读取当前 row state；不得仅检查 prepare INSERT 事件捕获的旧 `NEW.state`。任何 prepared 行在 commit 时存在都必须使整个 rotation、old-token 状态、新 token、JTI、family 更新和 replay 一起回滚。

## 4. AAD、响应和重试

应用只能用 prepare 返回的 `replay_id` 与 `expires_at` 构造基础契约第 18.3 节的 exact AAD。AES-256-GCM nonce 必须是每行独立的 12-byte CSPRNG 值。finalized encrypted envelope 保存首次成功响应的 exact status、三个允许的 headers 和 body bytes；重试不得重建 `X-Request-ID`、token 或 JSON。

refresh plaintext envelope 的 wire format 与 issuance 分域，固定为以下 LF 文本；占位符替换为首次响应的 exact bytes：

```text
AEGIS-REFRESH-RESPONSE-V1
status:200
header-count:3
header:Cache-Control:no-store
header:Content-Type:application/json
header:X-Request-ID:<首次请求的 exact request id>
body-length:<exact body byte count 的无前导零十进制>
body-b64u:<exact body bytes 的 canonical base64url-no-padding>
```

每行和末行都必须有一个 LF；禁止 CRLF、额外/缺失/重排字段、Unicode normalization、header 大小写变化、自动 JSON map 重序列化或新 request id。header 顺序就是上面的 ASCII 名称顺序。`status` 只允许 200，`header-count` 只允许 3；`body-length` 必须 canonical 且与 b64u 解码后的 byte count 相等。解密器必须先验证完整域标签、精确七个后续字段、唯一字段、顺序、allowlist、LF 与 canonical b64u，再以 constant-time compare 验证 `SHA-256(exact body bytes)` 等于 row 的 `response_body_hash`；任一失败均视为不可恢复的 replay 验证失败，不能返回部分响应或重新签发。

同 old token 的重试只有在 refresh request id、body hash、stable replay request hash、device 和 key fingerprint 全部匹配，row 已 finalized，数据库时间仍在 30 秒窗内，且 device/session/family/JTI 仍 active 时才可返回原 envelope。每次重试使用新的 PoP nonce/signature，但稳定 replay hash 不变。任何 mismatch、过窗、unknown kid/version、错误 nonce/tag/AAD、解密失败或 terminal principal 必须 fail closed；需要 compromise 的条件按基础契约在独立受限函数和同一风险事务处理，绝不重新签发。

## 5. 强制验收门

真实 PostgreSQL 18 双连接和故障注入至少覆盖：

1. prepare 后未 finalize 就 commit，deferred trigger 拒绝且 old token/new token/JTI/family/replay 全部回滚；
2. prepare 与 finalize 同事务成功，断连后用 fresh PoP nonce 和相同稳定字段取回逐字节相同响应；
3. finalize 在不同事务、二次执行、错误 tenant 或错误 envelope 元数据时拒绝；
4. 两个并发 refresh 只有一个 generation+1；另一个只能在完全相同且仍在窗口内时读取 finalized replay；
5. response encryption、replay INSERT、finalize 或 commit 任一点失败都不发送成功响应；
6. ciphertext/tag/AAD/kid/version 变更或 key 缺失不会消费或恢复 credential，也不会重新签发；
7. 30 秒边界和 `expires_at+120s` GC 边界使用数据库时钟精确验证；GC 永不删除 prepared 行；
8. catalog 证明表为 FORCE RLS、PUBLIC 零权限、runtime 无 base DML，函数 owner/signature/search_path/EXECUTE allowlist 精确；
9. 成功路径证明 PoP nonce 在 prepare 前原子消费，`consumed=false` 路径不调用 prepare 且只提交所需脱敏 replay risk/audit；required refresh.rotate success audit/risk facts 在 finalize 前写入并随同一事务提交；finalize/commit 故障时事务外仅产生脱敏 failure 事实；
10. `new_refresh_expires_at=least(family_absolute_expires_at, v_db_now+7 days)`，且 `refresh_expires_in` 对微秒边界、family absolute 提前到期、0 秒与最大 30 天均按本文整数公式得到唯一值；
11. refresh envelope 的 domain、LF、header 顺序/allowlist、body length/b64u/body hash 正负向量逐字节通过；
12. 日志与证据不包含 token、ath、完整 fingerprint、plaintext envelope、ciphertext、keyring JSON 或 key bytes。

上述任一门失败，refresh rotation 和整个 CLIENT-AUTH 生产发布均为 NO-GO。本附录当前仅冻结实现合同；migration42+、网关、Rust/Kotlin 交叉向量和生产 keyring 尚未完成。
