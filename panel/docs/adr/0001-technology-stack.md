# ADR-0001：技术栈选型

- 状态：已采纳
- 日期：2026-07-25
- 相关需求：NFR-001、NFR-002、DATA-001/002/003、PAY-005、AGT-001..012、CLI-001..014

## 背景

PRD 未锁定技术栈。附录 B 把 Xboard（PHP/Laravel）列为业务基线参考，
11.2 建议客户端采用「Rust/Go 共享核心」。需要在立项阶段冻结主栈。

约束条件：
- 首发服务器为 1 vCPU / 1.9 GiB 内存，且已运行其他业务
- 企业版目标：核心 API 可用性 99.95%、P95 < 300ms（15.1）
- Node Agent 需在任意云主机上以单文件分发，且与控制面复用 mTLS 与签名逻辑

## 决策

**后端 Go 1.26 + PostgreSQL 18 + Valkey 8；前端 React 19 + TypeScript。**

## 理由

### 为什么后端选 Go

1. **Node Agent 是决定性因素。** AGT-001..012 要求 Agent 主动建 mTLS 长连、
   非 root 运行、只执行白名单任务、断联一小时仍自治。这要求单文件、无运行时依赖、
   跨平台交叉编译。同时 AGT-007 的配置验签、USE-001 的用量事件签名必须与控制面
   使用完全一致的实现 —— 两端同语言才能共享这段代码而非各写一遍。
   Go 是唯一同时满足「单二进制分发」与「与后端同语言」的选项。

2. **内存约束。** 首发机器可用内存不足 1 GiB。Go 的常驻内存在本项目的四域网关下
   约 20–40 MiB/进程；JVM 与 Node 都要数倍于此。实测 Public 网关稳定在 ~25 MiB。

3. **并发模型贴合形态。** 支付回调、Agent 心跳、用量上报都是高并发短事务。
   goroutine + 连接池的开销远低于线程池，且 `context` 让 NFR-002 要求的
   「所有外部调用定义超时」有语言级的统一表达。

未选 PHP/Laravel：Xboard 的业务模型可以借鉴，但本项目要重构的恰是
账本、节点身份、mTLS、工作流编排这些 Laravel 生态支持薄弱的部分，
基线的复用价值主要在**数据模型**而非**代码**。

未选 Node/TypeScript 做后端：前后端同语言的收益，不足以抵消 Agent 端
无法复用代码、以及内存占用的劣势。

### 为什么数据库选 PostgreSQL 18

1. **内置 `uuidv7()`** 直接兑现 DATA-001「UUIDv7 或等价有序唯一 ID」，
   无需扩展或应用层生成，且索引局部性远好于 UUIDv4。
2. **行级安全 + FORCE RLS** 让 DATA-002「查询遗漏租户条件时由防护层阻断」
   成为数据库强制的性质，而不是靠代码review。
3. **DEFERRABLE 约束触发器** 使 PAY-005 的复式记账配平可以在事务提交时校验，
   允许事务中间态不平 —— 这是复式记账的必要条件。
4. **RANGE 分区**支撑 USE-004 的原始用量事件分级保留。
5. **`SELECT ... FOR UPDATE` 与 Serializable 隔离**支撑 XBD-012「并发购买不突破
   库存和次数限制」。

选 18 而非 17：`uuidv7()` 是 18 才内置的；且宿主机已有 `postgres:18-alpine` 镜像。

### 为什么缓存选 Valkey 8

协议与 Redis 兼容，但许可证是 BSD（Redis 7.4+ 已改为 RSALv2/SSPL）。
本项目将来若提供私有化部署版本，SSPL 会带来分发上的法律风险。

## 后果

### 正面

- 全部安全不变量下沉到数据库层，54 项不变量测试可脱离应用独立验证
- 单二进制部署，无运行时依赖，容器镜像可基于 scratch
- Agent 与控制面共享签名与身份代码

### 负面与缓解

- **Go 的 ORM 生态弱于 Laravel/Rails。** 本项目直接用 pgx + 手写 SQL。
  代价是样板代码多；收益是每条查询的执行计划可控，且 RLS 与 CTE 这类
  PostgreSQL 特性不会被 ORM 抽象层挡住。将来若样板代码成为负担，
  引入 sqlc 从 SQL 生成类型安全的 Go 代码，而不是引入运行时 ORM。
- **前端与后端语言不同。** 通过 OpenAPI 3.1 契约（EXT-002）生成 TS 客户端弥合。
- **客户端共享核心的语言待定。** Go 可以编译为 c-archive 供 Tauri/移动端调用，
  但 Rust 在这个场景的生态更成熟。该决策推迟到阶段 7（Windows 客户端）再做，
  届时另开 ADR；当前不影响后端与 Agent。

## 被否决的方案

| 方案 | 否决原因 |
|---|---|
| PHP + Laravel | Agent 端无法复用；账本与工作流需大量自建 |
| Node + NestJS | 内存占用高；Agent 分发需打包运行时 |
| Rust 全栈 | 开发速度代价过大，团队规模（18.2 建议 3–4 名后端）撑不住 |
| MySQL | 无 RLS，DATA-002 只能靠应用自觉；无 DEFERRABLE 约束触发器 |
