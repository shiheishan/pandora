# Pandora 新界面：第一轮可集成候选

本目录是独立 React 工程，接入现有 Go API。它已经替换首批连续业务操作的页面实现；**28 个 Admin 导航和 9 个 Portal 导航可进入真实业务组件，不代表全部旧操作已迁完，也不代表生产端到端验收通过。** 页面没有嵌入旧 HTML 或通用 JSON 编辑器。

## 开发与构建

工作目录：`panel/frontend`。Node 版本按 `package.json` 的 `engines`（`>=22.12.0`），CI 用 Node 22；所有依赖用 `package.json` 与 `package-lock.json` 精确锁定。

```bash
npm ci
npm run dev:admin      # 另一个终端可运行 npm run dev:portal
npm run typecheck
npm test
npm run build
npm run check          # typecheck + vitest + build，CI 跑的就是这一条
```

vitest 全局 `testTimeout` 为 30 秒、`maxWorkers: 2`：antd + jsdom 的重页面在 2 核 CI runner 上单例可超 10 秒。用例不再各自传超时参数。

开发服务只绑定 `127.0.0.1`，Admin 5173，Portal 5174。默认同源代理分别连接 `127.0.0.1:9001` 和 `127.0.0.1:9000`。需要不同 API 目标时显式配置 `VITE_PROXY_TARGET`，需要路径前缀时显式配置 `VITE_API_BASE`，不从当前深层路由猜测 API 地址。不得将开发代理误指向生产写接口后运行夹具。

输出为 `dist/admin`、`dist/portal`。`panel/` 下 `make frontend-embed` 执行 `npm ci && npm run build`，把两个目录完整同步进 `panel/web/admin/app`、`panel/web/portal/app`（排除 `.vite/`），由 `go:embed` 编进网关；`deploy/build-release.sh` 在 Go 构建前强制执行它，没有 npm 即失败。脚本采用相对 `base: './'`。入口 `/app/`，HashRouter 路由例如 `/随机管理前缀/app/#/users?page=2&q=test`。HTML 内 `pandora-api-base="../"` 相对实际入口页解析，保留反向代理前缀。Go 侧 `internal/platform/webapp` 负责 `/app` 到 `app/` 的相对重定向、显式 MIME、`assets/` 一年 immutable、入口 no-cache 与 ETag、缺失资源 404；不做业务路径 SPA rewrite。入口 CSP 是 `script-src 'self'`：构建产物不得含内联脚本，`panel/web/app_test.go` 对嵌入的真实产物检查这一点。

### 待接后端契约

本工程里有一批页面是按尚未落地的后端契约写的。它们的路径与权限码集中登记在 `src/core/contracts.ts`，入口默认关闭，只有入口 HTML 的 `<meta name="pandora-contracts" content="a b">` 或构建时 `VITE_PANDORA_CONTRACTS="a b"` 显式列出才显示。`npm test` 里的 `tests/api-surface.test.ts` 会扫描 `src/` 全部 `v1/` 路径与权限码，对照 `internal/api/admin/router.go`、`internal/api/public/router.go` 与迁移里的权限字典：未登记又不存在的路径直接失败，登记了但后端已经提供的也失败，所以登记表不会过期。

| 契约 | 前端入口 | 缺什么 |
| --- | --- | --- |
| `balance-operation-v1` | 用户详情的余额调账回查按钮 | BE1：`POST users/{id}/balance` 接受 `operation_id` 与 `amount_minor`，`GET balance-adjustments/{operationID}`；现行后端只接受整数 `amount` |
| `refunds-be4` | 订单详情的“退款待核对”“退款申请与审批”两个标签 | BE4-B1/B2 全部退款路径与 `billing.refund.execute` 权限码 |
| `reconcile-be4` | 订单详情的“主动查单”按钮与标签 | `POST orders/{id}/reconcile`、`GET orders/{id}/reconciliation-jobs` |
| `route-groups-v1` | 路由管理默认页、节点编辑的路由组多选 | `v1/route-groups` 资源；现行后端只有逐节点 `nodes/{id}/routing` |
| `coupon-edit-v1` | 优惠券列表的“编辑” | `POST coupons/{id}`；现行后端只有创建、批量与启停 |
| `mail-template-preview-v1` | 通知模板的“预览草稿” | `POST mail/templates/preview` |

后端补齐某项后：删掉 `contracts.ts` 里的条目（否则测试报“已提供却仍登记”），再把名字写进入口 HTML 的 `pandora-contracts`。

### 旧页迁移清单

生产入口仍是 `panel/web` 的两份手写单页。它们调用、而 React 还没有调用的 v1 路径逐条登记在 `tests/legacy-parity.ts`（按 admin / portal 分域，附旧页用途）。`tests/api-surface.test.ts` 解析旧页里 `'/v1/orders/' + id + '/mark-paid'` 这类字符串拼接，按域对照 React 源码（`features/admin`、`features/portal` 各归一域，其余共享代码两域都算），要求“旧页有、React 没有”的集合恰好等于清单：React 补上一条而没删登记、或旧页新增一条而没登记，都会失败。清单只会缩小，按页迁移、一页一轮，归零即具备把 `/` 切到 React 的条件。

React 19.2.8、TypeScript 7.0.2、Vite 8.2.2、Ant Design 6.6.2、TanStack Query 5.102.8、React Router 7.18.3、Zod 4.5.4。Admin/Portal 共享源码和资源依赖，但身份键、API 域与查询键独立。JWT 仍使用既有 localStorage 键，尚未迁移到 HttpOnly Cookie；不能把新 UI 宣称为新的会话存储安全体系。

### 错误、权限与资金契约

- 先识别 `reauth_required`，再处理普通 401；普通 403 是权限拒绝。兼容旧中文重认证错误。重认证弹窗有独立 AbortController，关闭后迟到结果不得替换访问令牌。
- API 网络异常、超时和服务器异常不会显示成功；列表首次加载失败显示错误和重试，已有列表刷新失败保留原数据并显示警告。缺失列表字段不会被解释为成功空列表。
- 导航读取权限和具体按钮写权限分开，最终权限仍由 API 验证。`POST users/{id}/balance` 的当前真实权限为 `billing.provider.write`，查询调账结果另需 `billing.ledger.read`；不能因为新金额字段而擅自改为 `billing.adjustment.write`。
- 余额调账的 BE1 契约（UUID `operation_id`、十进制字符串 `amount_minor`、按操作号回查）尚无后端，登记为待接契约 `balance-operation-v1`。默认构建走兼容接口，发送整数 `amount`、币种与原因，仍拒绝超过安全整数的旧 JSON number。没有 capabilities 接口：契约开关只来自入口 HTML 的 `pandora-contracts` meta 或 `VITE_PANDORA_CONTRACTS`。
- 余额调账发送前保存固定主体、URL、方法、金额、币种、原因和操作 ID；同标签刷新后可重放完全相同参数，打开 `balance-operation-v1` 后还可查询 `GET balance-adjustments/{operationID}`。查询 404 仍为待核实，不能由此创建新意图。不同主体不能恢复此记录；只有 ID 而没有原始参数时须人工核对，不自动补造请求。待核实资金意图不按普通草稿的 24 小时规则删除。
- 其他 `Operation` 提供本页面内的请求合并和重试身份，**不能据此宣称每个旧 API 都实现后端幂等，也没有跨设备恢复保证。** 服务端未提供可核对结果的动作仍需业务核对。
- 主动查单属于待接契约 `reconcile-be4`，默认不显示入口。`POST orders/{id}/reconcile` 的 202 只表示任务提交。订单、支付、开通、查单状态分别显示；`synced` 显示“支付事实已同步”，不直接把订单改成已开通。
- 退款工作台属于待接契约 `refunds-be4`，默认不显示入口；权限码按后端字典使用 `billing.refund.request` 与 `billing.refund.approve`，`billing.refund.execute` 尚不在字典里。退款通知待核对接口未提供订单关联，UI 明确显示全租户最多200条的队列；未知金额不作零，通知接收不作冲账。退款预览、按来源分配申请、列表/单号查询、审批、执行入队与已知外部凭据登记按 BE4-B1/B2 编写，该后端不在本仓库。列表只包含全租户最近100笔，页面不宣称完整订单历史，提供操作号直查。申请operation_id、审批/执行/凭据action_id及expected_version分别冻结；审批未知时仅GET当前状态不能证明原动作完成。requires_second_reviewer由服务端冻结，字段缺失时暂禁申请人自批准；本人有审批权限时可填写原因撤回。
- 执行POST的202只表示持久入队。入队HTTP回执丢失时先查询；若仍approved，提供“按原操作核对或重试入队”，完整复用action_id和原参数。后台operation已经unknown时禁止再次执行渠道退款，仅核对资金或登记外部事实。原execute回执确认后不再显示重放入口；各状态都不自动产生新资金意图。
- 人工凭据表单只针对原payment分腿，金额/币种固定且必须明确勾选已核实渠道退款。可选本机文件（≤32MB）在浏览器计算SHA256，文件不上传；管理员必须填写可复核的归档位置或渠道记录。高级区允许已有校验值输入。凭据草稿按主体/分腿隔离，提交前冻结全部参数。登记后本地入账失败使用原action/原凭据重试，本接口不再发渠道退款；processing期间若worker持有执行权，后端可409拒绝新凭据，表单保留输入。
- 退款详情分开显示awaiting_evidence、provider_succeeded和ledger_succeeded；渠道已退但本地未入账不得显示完成。EPay仍需要人工渠道退款与证据登记，demo_hmac仅测试适配器；充值、历史续费、含佣金及复杂权益组合仍由后端返回人工原因。跨设备或仅剩操作号而没有原冻结参数时只查询和人工核对，不编造新action或证据；本轮没有凭证上传/托管服务。
- Node 新增需要 `node.provision`；服务器资料创建/编辑是 `node.write`。节点“启用/停止下发”使用 `/nodes/status:batch`，传单条 `items[id,row_version]` 与 `serving_status`；它不使用旧 `/nodes/{id}/status` 生命周期接口。

### 核心连续任务与限制

1. 用户处理：检索→详情→状态/分组/调账/流量重置→近期订单/相关工单。表单 API 失败后原文保留。资金未知结果只能沿原操作查询或重放。
2. 节点接入：服务器资产→一次性命令→服务端心跳→逻辑节点及协议/分组→服务显隐→套餐使用该分组。**命令需要目标主机执行；这不自动创建每个逻辑节点的独立身份。** 原生 enforced 模式要求各逻辑 NodeID 使用匹配的 IdentityPath；UI 不宣称数据面已通过。
3. 套餐购买：Admin 整体创建/发布→Portal 选择周期/优惠码/余额→服务器创建订单→EPay 链接→订单支付状态→订阅。数据面的实际连通及真实渠道支付仍由集成验收确认。
4. 续费：从现有订阅选择周期→创建该订阅的续费订单→同一订单支付路径。当前续费对话传 `use_balance:0`；不要声称已覆盖余额续费所有组合。
5. 工单：Portal 创建/回复→Admin 指派/回复/内部备注→关闭；背景刷新不改写正文草稿。内部备注只在管理界面显示。
6. 退款：订单→预览真实来源→明确分配和权益策略→冻结申请→按服务端双人策略审批→执行入队→跟踪渠道/账本分态；人工渠道确认后登记凭据。各步骤失败不丢原参数，队列回执丢失和渠道结果未知走不同恢复路径。前端组件回归与真实后端/渠道验收分别记录。
