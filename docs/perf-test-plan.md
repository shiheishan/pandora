# 换栈后的性能测试（P8 第一轮）

用户 2026-10-13 定：P8 第一轮只测下面四项，测完看结果再决定优化什么。分析方法是先把面板、节点、用户当一个整体，再看各部分，再看它们之间的关系；占用问题先分清「在做产品需要的工作」和「在弥补某个设计」，再动手。

## 测什么

1. **面板静默占用**：没有用户操作、只连着节点时，面板、PostgreSQL、Redis 的 CPU 和内存，拆成「固定部分 + 每台服务器多少」。用来检验新的节点通道（每台服务器一条 gRPC 会话、面板直接终结 mTLS、变化推送、按版本对齐）有没有消掉 2026-10-09 诊断出的那批根源：nginx 终结 TLS、一节点两套协议、轮询为主、定时全量上报、按节点建连接。
   - 顺带核对：心跳每次写不写库；流量上报每份写多少行、主键是不是随机的；建连对齐时算名单版本贵不贵。
2. **每个请求的数据库往返和慢 SQL**：订阅拉取、门户读写、后台列表与看板。换了 ORM，最容易出现一次请求发几十条 SQL。
   - 看每个热点接口发几条 SQL、调几次 Redis，热点 SQL 在造好的数据上的执行计划。
3. **三个突发**：
   - 整点批量到期：大量订阅同时到期，名单增量扇出到所有服务器，断线要几秒；
   - 面板重启后批量重连：1000 台服务器同时握手、查身份、比版本，面板多久恢复；
   - 群发：一次给几万人发邮件或站内信，会不会拖慢在线请求。
4. **节点转发**：P5 没动转发代码，优先级低。要测的是 1 万人名单怎么应用到内核（增量还是重建入站）、应用时会不会断开已有连接。

## 怎么测

- 环境：同机房 VPC 里 1 台面板机和几台压测机，测试流量只走内网地址；造 1 万用户、1000 节点，并带上历史数据（流量明细、订单、审计、过期用户），空表测不出真实速度。
- 旧成绩单（2026-10-09 那轮：2c4g，1 万用户、1000 节点）只当对照数字用，不再跑旧工具。旧的 `panel/tools/loadtest` 引用旧代码，随 P7 删除；新工具在 P7 期间准备：
  - 节点：在 `pdnd/release/nodesim` 上扩到能同时开 1000 个会话；
  - 用户：k6 按固定到达率加压，阈值判过不过；
  - 观测：面板加 Prometheus 指标（HTTP、gRPC、连接池、Redis、队列），测试机装 node_exporter、postgres_exporter，打开 pg_stat_statements，需要时开 pprof。
- 纪律：压测机和面板机分开；以服务端计时为准；先预热再取稳态窗口；同一场景至少跑 3 次；每次记下提交号、机型、配置、数据量；一次只改一个变量。结果放 `ops-local/`（含现场地址，不入库）。
