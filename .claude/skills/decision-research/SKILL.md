# 产品决策调研

目标：让用户在看得懂的证据上做决定，而不是在两个都说得通的方案里凭感觉挑。2026-10-07 购买模型统一（多订阅、抵扣、流量包归属）就是这样定下来的，产物在主目录 `.claude/purchase-*.md`。

取舍口径见根 CLAUDE.md「取舍原则」。

只管产品规则：用户看得到的行为、钱、链接、习惯，最后由用户拍板。工程、架构、协议上的「别家怎么做」（上游源码、协议规范、事故复盘）走 prior-art-research：那边按领域分路、产物进 `.claude/<主题>-kb/`、工程取舍总协调按原则自己定。一题两面都有的（例：Brutal 公平性），先在 prior-art-research 查事实，产品那一面再按本 skill 第 5 步交用户。

## 步骤

1. **先查现状**（执行者：一个只读子 agent；涉及钱、权限、迁移用 `opus`）：系统现在实际怎么做，每条给文件:行号，存成主目录 `.claude/<主题>-survey.md`。不查现状就调研，会把已经存在的能力当成要新做的，也看不出新方案和旧守卫哪里冲突。
2. **写问题清单** `.claude/<主题>-questions.md`：背景一段、用户的设想原话、已定的（D1、D2…）、待定的（Q1、Q2…，每题写候选方案）、评判标准。三路都读这一份，口径一致。
3. **并行派三路**（互相看不到结论，免得一路带偏另外两路），每路逐题回答并给证据：
   | 路 | 看什么 | 执行者 |
   |---|---|---|
   | 同类产品 | 源码与社区抱怨（本项目是 Xboard、V2Board、SSPanel-UIM、PPanel），优先读源码，可 `git clone --depth 1` 到 scratchpad 只读。要上网 | `opus` |
   | 主流产品 | 官方文档：普通人的直觉是被它们训练出来的（应用商店、Stripe、Netflix、运营商、云服务、商业 VPN 等）。要上网 | `opus` |
   | 心智走查 | 不上网。定 4–5 个画像，让每个画像走每个候选方案：点之前以为会怎样、实际怎样、选错能不能挽回、代价多大 | `opus` |
   三路都派 `opus`，只读、后台、同一条消息并行。要上网、要判断，根 CLAUDE.md 的 sonnet 只用于浏览器、改服务器和 opus 的下手，拿不准按 opus。cursor-agent 能否上网未核实，要上网的调研不交 Composer；某路里规则写死的本地盘点（例：列出系统里所有动余额的入口）可以交 Composer `--scan`（composer-handoff 第 4b 节）。
   每路报告存成 `.claude/<主题>-research-<路>.md`（子 agent 的最终消息由总协调代存）。
4. **综合一页** `.claude/<主题>-synthesis.md`：表格「题 | 走查 | 主流 | 同类 | 结论」，标出一致、冲突、无先例；每题一句推荐。三路的事实（尤其「某产品这样做」）抽查几条再写进去。
5. **给用户拍板**：
   - 先给综合表，再只把**冲突或无先例**的题单独举例讲清楚：用一个具体人物、具体数字的例子（「小王两份订阅、买了 50G 流量包，这 50G 给谁用」），不用机制词。
   - 用户回复「都行、拿不准」的题，再派一路针对性调研（例：余额要不要能输入金额），不要替用户定。
   - 定下的逐条写进 `.claude/TASKS.md` 对应条目和长期记忆的产品规则文件，原话保留。
6. **定完再验证体验**：会改界面的，先做原型并按 ux-review skill 测，过了再写实现设计。

## 坑

- 主流产品那一路常只拿到搜索摘要（官方页 403/503）：报告里要标「摘要」，综合时不要把摘要级证据当结论。
- 同类产品多数是「一人一订阅」，很多多订阅问题它们根本不存在：写「无先例」，不要硬套。
- 走查那一路最容易发现「已定方案里的坑」（例：套餐卡默认「换掉现有」会让用户撤不回），综合时单列出来提醒用户，即使用户之前已经定过。
- 用户的问题常是「这样新手看得懂吗」：这类问题调研给不了答案，只能原型加测试。
