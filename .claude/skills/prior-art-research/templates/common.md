## 要求

- **只读**：不改仓库、不提交、不登录服务器，不读 `ops-local/**/secrets/` 与 `*cred*` 文件。开源项目可以 `git clone --depth 1` 到 `<总协调 scratchpad>/<主题>kb-src/`，只读源码，不执行其中的构建脚本或代码；clone 后记下 sha。本机 go 命令加 `GOTOOLCHAIN=go<go.mod 版本>`，不和 `npm ci` 并发。<可选：可以在 scratchpad 写本机微基准验证关键说法，写明命令和数字。>
- **来源分级**：一手（RFC、规范、官方文档、上游源码 `仓库@sha 文件:行`、论文、维护者写的工程博客或演讲）> 维护者在 issue / PR 里的说法 > 第三方博客。每条结论标链接和级别；只读到摘要的标「摘要」；凭记忆的标「记忆，未核」。版本敏感的写版本号。摘要级和记忆级不能单独撑起「必须改」。
- **不抄原文**：用自己的话总结，引文每条不超过 15 个字，附链接。
- **必须落到 pandora**：每条经验写 pandora 现在（或设计里）怎么做，给仓库相对全路径的 文件:行（写 `pdnd/internal/nativewire/hysteria2/service.go:245`，不写 `hysteria2/service.go`，同名文件不止一个），判断「已一致 / 有差距 / 我们更好 / 不适用」。说到某种写法有问题时，grep 出它在 pandora 的全部出现处，不只举一处。
- **有差距的按取舍原则写**：性能、用户体验、安全、可维护性四栏逐项写「变好 / 不变 / 变差」和依据（实测 / 读码 / 推测），写预期收益和风险。任一栏变差的标「不采用」并写原因。不建议拉长间隔、降低实时、削弱安全、改内核参数（sysctl、THP 一律只能进「不采用」）。
- **专门找反例**：别人在这条路上踩过的坑（规模上去后的瓶颈、事故复盘、issue 区的真实故障），对照 pandora 现状或设计会不会踩。
- **事实与推测分开**：拿不准的写缺什么证据、用什么实验能定（本机微基准、VPC 复测项、真机客户端）。
- **产品取舍不替用户定**：查到的分歧如果改变用户看得到的行为（谁多拿带宽、打开节点域名看到什么），把事实和候选方案写进附 4，不在正文里选定。
- **拆下手**：要上网或要判断的，派 `opus` 子 agent，并且前台派（`run_in_background: false`）：后台子 agent 的完成通知会落到总协调，不回到你这里。规则写死的本地盘点（列出全部调用点、逐条核 文件:行）可以交 Composer 的 `--scan`，做法见 `/Users/a1/ai/projects/pandora/.claude/skills/composer-handoff/SKILL.md` 第 4b 节，`--log-dir` 用 `<总协调 scratchpad>`。下手交回的关键行你自己抽查，报告开头写抽查了几处。
- **篇幅**：约 <400–700（新领域）/ 150–300（补缺口）> 行 markdown。先一页结论（最重要的 3–7 条，按影响排序），再分节；正文要有「不采用」一节。
