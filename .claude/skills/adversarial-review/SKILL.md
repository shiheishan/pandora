# 合并前的对抗式审查

目标：会动钱、权限、秘密、迁移、节点内核的分支，合并前由一个没参与实现的 opus 专门挑毛病，按同一套标准审、按同一种格式交回。历次审查大多查出了要返工的问题，例如 w7buya 的免单范围、w12native 迁完再跑 install.sh 会切回旧库。验收的其余步骤见 accept-task skill。

## 1. 要不要审

在主目录跑（只读）。`<上游>` 是该路 brief 写的上游分支：一般是主线 `feat/panel-redesign`，叠在集成分支上的路给集成分支（如 S 的 `feat/panel-redesign-s`），见 dispatch-task「叠在集成分支上的路」：

```bash
python3 .claude/skills/adversarial-review/scripts/triggers.py <上游> <分支> [--composer]
```

- 退出 0：有触发，必须审，输出按领域列出命中的文件和新增行。退出 1：不必审，仍按 accept-task 自己读关键 diff。退出 2：范围是空的，分支多半已经合入；事后补审时用合并提交的两个父提交，写成 `M^1 M^2`。
- **执行者是 Cursor 的 Composer 时加 `--composer`**：根 CLAUDE.md「大任务拆子 agent」要求 Composer 交回的分支除小件外都派 opus 审，不看领域命中。小件 = 领域无命中，且非测试文件增删合计不超过 30 行（脚本的 `COMPOSER_SMALL`，二进制文件按超限算），这时退出 1；其余退出 0。小件不审，也要自己读全部 diff。
- 基点要给上游分支名，不要给 brief 里的原基点。分支中途合过上游时，原基点会把合进来的上游改动也算进去：w7pdnd 应该是 43 个文件，用原基点算出来是 161 个。叠在集成分支上的路给了主线，前面几路已合进集成分支的改动也会算进来。
- 脚本只看路径和新增行，结果只是线索。下面几种情况脚本可能没命中，也要审：
  - diff 删掉或放宽了某个拒绝条件，包括 409、422、403、触发器、约束。例：w10fix 放开了「控制节点可以批量退役」。
  - 改了面板或节点处理未认证请求的方式。
  - 新加了后台 worker 或租约。
- 命中了但可以不审：只改了测试、注释或文案（用 accept-task 的 `comment-only.sh` 证明），或者是纯挪动（refactorcheck 结果为 PURE MOVE）。Composer 的分支同样适用：这两种有脚本证明，比审查更硬。

## 2. 派审查员

- **时机**：实现方交回报告后就派，和等 CI 并行。prompt 里写死分支头的 sha，实现方之后再推的提交不在这次审查范围内。
- **人选**：opus，后台运行，每个分支派一个。不要让实现方自己审自己。
- **prompt**：用脚本按 `templates/reviewer-prompt.md` 生成，只读：

  ```bash
  python3 -I .claude/skills/adversarial-review/scripts/review-prompt.py first <上游> <分支> \
      --what "<一句话内容>" --scratchpad <总协调的 scratchpad> [--design <设计稿>] -o <scratchpad>/prompt-<名字>.md
  ```

  merge-base、头的完整 sha、shortstat、副本路径与 archive 命令、检查表节名（取触发脚本命中的领域）、材料路径、`GOTOOLCHAIN` 版本（从 go.mod 读，升 Go 不用改模板）都由脚本填好，只剩「这次的重点」要人写。脚本报「占位没替换干净」或「checklist.md 里没有这些节」，说明模板或节名改过，先同步脚本。
- **「这次的重点」写 3–7 条**：从 brief 的任务和设计稿里风险最大的决定里挑。每条写清改了什么机制、担心出现哪种错误结果。brief 和设计稿只给路径，不要整段贴进 prompt。可以参考的写法：w7buya 写的是价格篡改与重放、余额冻结成对、并发锁序、礼品卡落点；w9cert 写的是秘密只存密文、权限与重认证、租约、生产环境拒绝测试开关、新依赖。
- **登记**：在 `.claude/TASKS.md` 记下审查员的 agent ID。会话中断后凭这个 ID 用 SendMessage 续跑。
- **耗时**：一次通常 11–16 分钟，20–32 万 token（w7buya 到 w10fix 试跑的实测）。
- **存报告**：审查员交回后，用 accept-task 的 `scripts/save-report.sh <output 文件> ../pandora-<名字>/.claude/review.md` 存下来。**发第二轮 brief（以及之后每一轮的修复消息）之前先存**：消息让对方先读它。w12native、w12quic 第二轮都是消息先到、报告后存，实现方读不到原文。
- **文件命名**：首轮审查 `review.md` → 第 2 轮修复 `report-r2.md` → 复审 `review-r2.md` → 第 3 轮修复 `report-r3.md` → 复审 `review-r3.md`，依此类推。`review-prompt.py` 按 `--round N` 自动取。

## 3. 总协调怎么核

审查员的报告只是线索。中危以上的每一条都要自己核过，才能写进下一轮修复消息：

- **中危以上，逐条核**：
  - 在分支头打开报告给的文件:行。分支已经前进的，按符号查找。
  - 顺着报告写的触发场景把代码走一遍：SQL 的 WHERE 条件、锁住的是哪一行、分支判断条件。
  - 报告附了探针的，自己重跑一次，看输出是否一致。
  - 核不实的，降级处理，或者用 SendMessage 让审查员补证据。没核实的结论不转给实现方。
- **「核过无问题」**：挑 1–2 条和本次重点相关的，自己看一眼。
- **低危**：通读一遍，按第 4 节分流，不必逐条核。
- **涉及产品口径的发现**（例：免单范围该多大）：用户定过案的，按定案的原意收窄，依据见 `rules/domain-billing.md` 等规则和 memory 里的产品决定；没定过的，列进「需要用户定」。w7buya 的 F1 就是按用户第 8.1 题的原意收窄的，并在汇报里写明「想改再告诉我」。

## 4. 结论怎么分流

| 发现 | 去向 |
|---|---|
| 高、中、低（本分支归属内） | 合并前下一轮全修 |
| 低，属于别的路，或者要改别人归属的文件 | SendMessage 通知那一路（Composer 的路收不到，记进 TASKS，下次开工文件带上），或者记进 TASKS。例：w7buya F5「换报价后要换新的幂等键」转给了门户那一路 |
| 回滚口径、运维注意事项 | 写进 MIGRATION-RUNBOOK 或 docs，由总协调写或交给实现方 |
| 整合风险（本分支单独合入或单独发版会出问题） | 记进 TASKS 的发版前清单，不挡合入主线 |
| 审查员标为「疑似」、而且没补上证据的 | 不进 brief，记进 TASKS |

**第 N 轮修复消息**（N ≥ 2，第二轮 brief 即 N=2）照 `templates/round-brief.md` 写，骨架用 `review-prompt.py round <分支> --round N --scratchpad <…> [--executor composer]` 生成（填好名字、轮次、worktree、分支、依据的审查报告、交回文件名、探针目录、go 版本；`--executor` 选完成标准与交回的写法）。按原实现方分两条路：

- **Claude 子 agent**：用 SendMessage 发给原实现 agent，它对这块代码最熟；原 agent 的会话已经不在了，就按 dispatch-task 新开一个。
- **Cursor 的 Composer**：它收不到 SendMessage，修复轮写成文件另起一次。骨架加 `--executor composer -o <worktree>/.claude/round-r{N}.md`，补完留给人写的部分，再 `bash .claude/skills/dispatch-task/scripts/cursor-launch.sh <名字> --round N`。脚本让它先读根 CLAUDE.md、原 brief 与 `round-r{N}.md`，报告写 `report-r{N}.md`。新起的一次不记得上一轮，所以 round 文件里要写全：审查报告路径、核过的发现、探针路径。根 CLAUDE.md 把「审查后照清单的机械修复轮」划给 Composer；修法要做架构取舍、或上一轮 Composer 的证据核对不过的，改派 opus。复审照第 6 节，不因执行者不同而改。

模板之外要注意：

- 修法写方向，不写逐步操作；有多个方案时让实现方按根 CLAUDE.md「取舍原则」四栏逐项比较，在报告里写比较结果和选择理由（w9cert 第 2 项就是这样定了只追加的签发流水）。
- 迁移号要重新取：主线可能已经前进了。w9cert 第二轮原定的 00149 比主线已有的 00151 还小，只能改用 00152。叠在集成分支上的路用的是临时号，不重取（见 new-migration「集成分支的相对编号与重编号」）。
- 消息里写「我合并时改」的条目，当场登记进 accept-task「一波合并」表。
- 实现方交回后：**Cursor 的 Composer** 的路由总协调（或派一个 opus）先按 verify skill 本地验证、做回退实验、推送、等 CI，再存 `report-r{N}.md` 并派复审；**Claude 子 agent** 交回后用 save-report.sh 存成 `report-r{N}.md`。复审员要对着报告逐条核。

## 5. 什么时候可以合

- **默认**：高、中、低（归属内的）都修完、CI 绿了，再合。属于别的路归属的低危除外，转登记。
- **有高危**：一律先修后合。
- **可以先合后修**，只留一种情况：不合会挡住别的路，或者修复要用到主线上的东西。同时要满足：
  1. 没有高危；中危不涉及钱、越权和明文秘密。
  2. 修复轮已经派出、记进了 TASKS，并且标为首发前必须合入。

  先例是 w9cert：2 中 11 低，先合入 fdc0ae2，再派第二轮。

- **审查员说「可合」，也可以先退回去修**，适用于三种情况：新暴露了未认证就能利用的攻击面；资源占用按 1 核 1G 的节点算扛不住；踢人、吊销这类处置不能立刻生效。先例是 w7pdnd：审查员的结论是能合、没有必修项，总协调因为 XHTTP 未认证就能占住内存、踢人每条卡 5 秒，仍然退回先修。
- 向用户汇报时说清是先修还是先合，以及理由。对于先合后修的，要说明挡住了哪一路或修复用到了主线上的什么，以及首发前必须合入。

## 6. 每轮修完要不要复审

第 N 轮（N ≥ 2）修完后，只看**这一轮自身的 diff**（`<上一轮审查时的头>..<这一轮的头>`），命中下面任一条就再派一次复审，不设轮数上限：

- 新增了锁、名额、租约或 worker；
- 动了授权或属主（GRANT / REVOKE、SECURITY DEFINER、ALTER … OWNER、REASSIGN）；
- 新增或改了迁移、新表；
- 改了钱的口径；
- 修的是高危；
- 非测试 diff 超过约 500 行。

都不命中的，由总协调自己核：每条中危的修法 diff、对应的测试名出现在 CI 日志里、探针修前修后的数字。复审又发现中危以上的，进下一轮修复，修完照本节再判一次。

复审 prompt 用 `review-prompt.py rereview <分支> --round N --from <上一轮审查时的头> --scratchpad <…>` 按 `templates/rereview-prompt.md` 生成：范围（有合主线的提交时自动只取分支自己改过的文件，去掉只带进主线的合并）、shortstat、副本路径、材料文件名、新发现的编号前缀都填好，「派去修的」和重点自己写。上一轮的审查员还在时，优先用 SendMessage 发给它，它记得上一轮的探针。

原因与先例：

- 修复轮本身也会引入缺陷。w9cert 第二轮新增了 00152 和账号重注册的逻辑，CI 抓到一个就是这一轮自己带进来的：重注册后的新账号续期时还带着旧证书的 ARI replaces（1d313ca 修复）。那一轮当时没有复审，按这条规则应该复审。
- 第三轮也照此判（10-09 两例）：w12native 第三轮给旧格式备份补 SECURITY DEFINER 函数的属主与授权，命中「授权或属主」；w12quic 第三轮加了全局热态名额，命中「名额」。两次复审都只发现低危，可合。

## 7. 收尾

- 在 `.claude/TASKS.md` 记一行：几高几中几低、各自的去向、审查报告（`review.md` 或 `review-r{N}.md`）的路径。
- 收尾表加一行：对抗审查 | opus | 结论 | 审查报告路径与关键探针输出。
- 审查员报告末尾「对检查表的意见」里有价值的条目，补进 `checklist.md`，写上出处（分支名和发现编号）；审查员提的修法本身不进检查表。补条的规矩：
  - 先找能并入的已有条目：同一件事换了场景的，并进那条作例子或出处，不另起一条。
  - 写成可复用的检查项：标题写「查什么」，一路专属的细节（文件、平台、数字）放进括号作出处。
  - 放进会被触发的节：审查员只读「通用」「测试有效性」和触发脚本命中的节。要新开一节时，同步改 `scripts/triggers.py` 的 `AREAS`（节名和领域名不同时再改 `review-prompt.py` 的 `SECTION`），并用 triggers.py 对一个该命中的分支实跑一次。
  - 每轮 skill 审查时把检查表归并一次：合并重复、挪回放错节的条目，只合并或挪动，不删检查内容。

## 坑

- **PG18 相关的结论只是「读码」**：本机没有 Docker，审查员对 PG18 相关路径的结论只能读代码得出，要以 CI 的结果为准。
- **探针的位置**：审查员的探针放在总协调的 scratchpad 里。要让实现方收进正式测试，在 brief 里给出探针的绝对路径（w7pdnd 的 V2 就是这样做的）。
- **行号会过时**：行号以审查时的分支头为准。分支合过主线、或进了修复轮之后，按符号查找。
- **内置的 `/security-review`、`/code-review`**：可以加跑作补充，但不能代替本 skill。它们不知道本项目的锁序、RLS、追加写表、门槛顺序这些不变量。
