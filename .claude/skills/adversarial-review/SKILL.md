# 合并前的对抗式审查

目标：会动钱、权限、秘密、迁移、节点内核的分支，合并前由一个没参与实现的 opus 专门挑毛病，按同一套标准审、按同一种格式交回。历次审查大多查出了要返工的问题，例如 w7buya 的免单范围、w12native 迁完再跑 install.sh 会切回旧库。验收的其余步骤见 accept-task skill。

## 1. 要不要审

在主目录跑（只读）：

```bash
python3 .claude/skills/adversarial-review/scripts/triggers.py feat/panel-redesign <分支>
```

- 退出 0：有触发，必须审，输出按领域列出命中的文件和新增行。退出 1：不必审，仍按 accept-task 自己读关键 diff。退出 2：范围是空的，分支多半已经合入；事后补审时用合并提交的两个父提交，写成 `M^1 M^2`。
- 基点要给主线分支名，不要给 brief 里的原基点。分支中途合过主线时，原基点会把合进来的主线改动也算进去：w7pdnd 应该是 43 个文件，用原基点算出来是 161 个。
- 脚本只看路径和新增行，结果只是线索。下面几种情况脚本可能没命中，也要审：
  - diff 删掉或放宽了某个拒绝条件，包括 409、422、403、触发器、约束。例：w10fix 放开了「控制节点可以批量退役」。
  - 改了面板或节点处理未认证请求的方式。
  - 新加了后台 worker 或租约。
- 命中了但可以不审：只改了测试、注释或文案（用 accept-task 的 `comment-only.sh` 证明），或者是纯挪动（refactorcheck 结果为 PURE MOVE）。

## 2. 派审查员

- **时机**：实现方交回报告后就派，和等 CI 并行。prompt 里写死分支头的 sha，实现方之后再推的提交不在这次审查范围内。
- **人选**：opus，后台运行，每个分支派一个。不要让实现方自己审自己。
- **prompt**：用脚本按 `templates/reviewer-prompt.md` 生成，只读：

  ```bash
  python3 -I .claude/skills/adversarial-review/scripts/review-prompt.py first feat/panel-redesign <分支> \
      --what "<一句话内容>" --scratchpad <总协调的 scratchpad> [--design <设计稿>] -o <scratchpad>/prompt-<名字>.md
  ```

  merge-base、头的完整 sha、shortstat、副本路径与 archive 命令、检查表节名（取触发脚本命中的领域）、材料路径都由脚本填好，只剩「这次的重点」要人写。脚本报「占位没替换干净」或「checklist.md 里没有这些节」，说明模板或节名改过，先同步脚本。
- **「这次的重点」写 3–7 条**：从 brief 的任务和设计稿里风险最大的决定里挑。每条写清改了什么机制、担心出现哪种错误结果。brief 和设计稿只给路径，不要整段贴进 prompt。可以参考的写法：w7buya 写的是价格篡改与重放、余额冻结成对、并发锁序、礼品卡落点；w9cert 写的是秘密只存密文、权限与重认证、租约、生产环境拒绝测试开关、新依赖。
- **登记**：在 `.claude/TASKS.md` 记下审查员的 agent ID。会话中断后凭这个 ID 用 SendMessage 续跑。
- **耗时**：一次通常 11–16 分钟，20–32 万 token（w7buya 到 w10fix 试跑的实测）。
- **存报告**：审查员交回后，用 accept-task 的 `scripts/save-report.sh <output 文件> ../pandora-<名字>/.claude/review.md` 存下来。第二轮的复审存成 `review-r2.md`。

## 3. 总协调怎么核

审查员的报告只是线索。中危以上的每一条都要自己核过，才能写进第二轮 brief：

- **中危以上，逐条核**：
  - 在分支头打开报告给的文件:行。分支已经前进的，按符号查找。
  - 顺着报告写的触发场景把代码走一遍：SQL 的 WHERE 条件、锁住的是哪一行、分支判断条件。
  - 报告附了探针的，自己重跑一次，看输出是否一致。
  - 核不实的，降级处理，或者用 SendMessage 让审查员补证据。没核实的结论不转给实现方。
- **「核过无问题」**：挑 1–2 条和本次重点相关的，自己看一眼。
- **低危**：通读一遍，按第 4 节分流，不必逐条核。
- **涉及产品口径的发现**（例：免单范围该多大）：用户定过案的，按定案的原意收窄，依据见 `rules/domain-billing.md` 等规则和 memory 里的产品决定；没定过的，列进「需要用户定」。w7buya 的 F1 就是按用户第 8.1 题的原意收窄的，并在汇报里写明「想改再告诉我」。

## 4. 结论怎么分流

| 发现 | 去向 |
|---|---|
| 高、中 | 第二轮必修 |
| 低，改动小，而且在本分支的归属范围内 | 第二轮顺手修 |
| 低，属于别的路，或者要改别人归属的文件 | SendMessage 通知那一路，或者记进 TASKS。例：w7buya F5「换报价后要换新的幂等键」转给了门户那一路 |
| 回滚口径、运维注意事项 | 写进 MIGRATION-RUNBOOK 或 docs，由总协调写或交给实现方 |
| 整合风险（本分支单独合入或单独发版会出问题） | 记进 TASKS 的发版前清单，不挡合入主线 |
| 审查员标为「疑似」、而且没补上证据的 | 不进 brief，记进 TASKS |

**第二轮 brief** 用 SendMessage 发给原实现 agent，它对这块代码最熟；原 agent 的会话已经不在了，就按 dispatch-task 新开一个。照 `templates/round2-brief.md` 写，骨架可以用 `review-prompt.py round2 <分支> --scratchpad <…>` 生成（填好名字、worktree、分支、探针目录）。模板之外要注意：

- 修法写方向，不写逐步操作；有多个方案时让实现方选更好维护的，并在报告里写理由（w9cert 第 2 项就是这样定了只追加的签发流水）。
- 迁移号要重新取：主线可能已经前进了。w9cert 第二轮原定的 00149 比主线已有的 00151 还小，只能改用 00152。
- 实现方交回后，用 save-report.sh 存成 `report-r2.md`，复审员要对着它逐条核。

## 5. 什么时候可以合

- **默认**：中危以上都修完、CI 绿了，再合。
- **有高危**：一律先修后合。
- **可以先合后修**，但下面四条要同时满足：
  1. 功能还没有用户在用：没发过版，或者默认关闭。
  2. 没有高危；中危不涉及钱、越权和明文秘密。
  3. 不合会挡住别的路，或者修复要用到主线上的东西。
  4. 第二轮已经派出、记进了 TASKS，并且标为发版前必须合入。

  先例是 w9cert：2 中 11 低，功能还没上线，先合入 fdc0ae2，再派第二轮。
- **审查员说「可合」，也可以先退回去修**，适用于三种情况：新暴露了未认证就能利用的攻击面；资源占用按 1 核 1G 的节点算扛不住；踢人、吊销这类处置不能立刻生效。先例是 w7pdnd：审查员的结论是能合、没有必修项，总协调因为 XHTTP 未认证就能占住内存、踢人每条卡 5 秒，仍然退回先修。
- 向用户汇报时说清是先修还是先合，以及理由。对于先合后修的，要说明「还没有用户在用」这一前提。

## 6. 第二轮修完要不要复审

满足下面任一条，就再派一次审查员（复审最多一次）：

- 第二轮新增了迁移或新表；
- 新增了锁、租约或 worker；
- 改了钱的口径；
- 修的是高危；
- 第二轮的非测试 diff 超过约 500 行。

复审的范围只是第二轮的 diff：`<第一轮审查时的头>..<第二轮的头>`。prompt 用 `templates/rereview-prompt.md`，范围、shortstat、副本路径用 `review-prompt.py rereview <分支> --from <第一轮的头> --scratchpad <…>` 填，「派去修的」和重点自己写。第一轮的审查员还在时，优先用 SendMessage 发给它，它记得上一轮的探针。交回表固定为：上一轮编号 | 已修/部分修/未修 | 证据 | 回退是否变红，再加新发现表和「可合 / 修完再合」。

原因：第二轮本身也会引入缺陷。w9cert 第二轮新增了 00152 和账号重注册的逻辑，CI 抓到一个就是这一轮自己带进来的：重注册后的新账号续期时还带着旧证书的 ARI replaces（1d313ca 修复）。那一轮当时没有复审，按这条规则应该复审。

不满足上面任何一条的，由总协调自己核：每条中危的修法 diff、对应的测试名出现在 CI 日志里、探针修前修后的数字。复审又发现中危以上的，再修一次，由总协调核，不再派第三次审查。

## 7. 收尾

- 在 `.claude/TASKS.md` 记一行：几高几中几低、各自的去向、`review.md` 的路径。
- 收尾表加一行：对抗审查 | opus | 结论 | review.md 路径与关键探针输出。
- 审查员报告末尾「对检查表的意见」里有价值的条目，补进 `checklist.md` 对应的节，写上出处（分支名和发现编号）。审查员提的修法本身不进检查表。

## 坑

- **PG18 相关的结论只是「读码」**：本机没有 Docker，审查员对 PG18 相关路径的结论只能读代码得出，要以 CI 的结果为准。
- **探针的位置**：审查员的探针放在总协调的 scratchpad 里。要让实现方收进正式测试，在 brief 里给出探针的绝对路径（w7pdnd 的 V2 就是这样做的）。
- **行号会过时**：行号以审查时的分支头为准。分支合过主线、或进了第二轮之后，按符号查找。
- **内置的 `/security-review`、`/code-review`**：可以加跑作补充，但不能代替本 skill。它们不知道本项目的锁序、RLS、追加写表、门槛顺序这些不变量。
