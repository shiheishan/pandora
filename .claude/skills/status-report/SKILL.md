# 总进度汇报

目标：每次汇报口径一致、事实来自脚本与 TASKS.md，而不是凭记忆。用户问过很多次「总进度到哪了」，每次都重新翻清单、git 与 CI 既慢又容易漏。

## 取数

```bash
bash .claude/skills/status-report/scripts/snapshot.sh
```

只读，打印主线与 CI 现状、各任务 worktree 的进度、主目录 TASKS 的未完成项和「下一步顺序」（细节见脚本头注释）。

正在跑的后台子 agent 脚本看不到：以本会话收到的启动与完成通知为准，没收到完成通知的就是还在跑，不要猜它的结果。

## 汇报格式

1. 一句话结论：现在处在哪个阶段、离下一个里程碑还差什么。
2. **阶段表**（阶段 | 内容 | 状态）：已完成写 ✅ 与关键提交；进行中写 🔄 与当前一步；未开始写 ⏸ 与前置条件。阶段名沿用 TASKS.md「下一步顺序」的说法。
3. **正在跑的**：每路一行（路 | 在做什么 | 进度），进度用 worktree 清单的勾选数或提交数，不写百分比估算。
4. **卡点与风险**：CI 红（用 ci-triage 的结论）、推送故障、测试机占用冲突、还没达标的指标（给实测数与目标）。
5. **需要用户的事**：只列真的要用户做或决定的；没有就明说「不需要你做决定」。
6. 时间估算只在用户问「多久」时给，用已完成同类任务的实际耗时类比，并说明是估计。

## 坑

- TASKS.md 是唯一的任务清单。汇报前先把已经合入的项打勾，否则「未完成项」里混着早就做完的旧条目，汇报会失真（10-07 体检时发现几十条过期未勾项）。
- worktree 的清单勾选数只说明那一路自己记的进度；「未合 0」不等于 CI 已绿，CI 以主线那一节为准。
- 不要把子 agent 报告里的数字当成已验证的结论写进阶段表：总协调核过（重跑、CI、判分）的才写 ✅。
