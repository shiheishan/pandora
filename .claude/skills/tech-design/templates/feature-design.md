## 0. 结论先行

- 一句话方案；它让哪些难题消失了、剩下真正要做的几件事（编号）。
- 规则只写一处：新逻辑落在哪个包，谁调用它（不跑 SQL 的纯函数包优先）。
- 被替换的旧做法与退场时点（不留长期双轨）。

## 4. 数据模型与迁移

- 表与列的变化；RLS、授权（`configure-app-role.sql`）、追加写、触发器；保留表名不写进 Go 注释（`panel/migrations/RESERVED-TABLES.md`）。
- 迁移清单，号段 <起–止>（`next-number.sh` 取号，含在途分支），每个迁移写可逆性与 Down 口径（new-migration skill）。
- 存量数据怎么迁、回填耗时（大表用 bench-eval 量）、回滚会丢什么。
- 两路同改一个 `CREATE OR REPLACE` 函数时，写明谁先合、谁在谁的函数体上加（根 CLAUDE.md「环境与工具坑」）。

## 5. 后端与 API

- 新包、接口签名（契约先行：第一个提交就是契约，供其他路对齐）。
- 路由、权限码、重认证、幂等 scope（后台新模块按 new-admin-module skill 的登记点）。
- 对外 JSON 形状（前端照它对着假后端开发）。
- 分层：handler 和 middleware 不跑 SQL（`rules/api-handlers.md`、`rules/domain-layering.md`）。

## 6. 界面（门户 / 后台）

- 页面、文案（禁用词见 `rules/screens-portal.md`）、默认值；会动钱和链接的流程先做原型，按 ux-review 测。
- 前端金额、默认值一律由服务端算好下发。

## 7. pdnd 侧（不涉及就写「pdnd 不用改」并说明为什么）

- 协议与配置下发的变化、新旧兼容（老 pdnd 接新面板、新 pdnd 接老面板）、灰度期间行为。
- 节点内核改动的验证：subscription-e2e → node-e2e →（大流量）node-accept。

## 8. 性能

- 新路径的往返数、热路径 SQL 用 bench-eval 判分；整机影响按 perf-gate 做改前改后。
- 理论上必须发生的工作，与方案后的预计值。
