# 门户 · 工单、帮助、消息与邀请返利

外观（10-16 起）按样稿 `dev/prototype/portal-v5.html` 的 `#p-ref` `#p-tickets` `#p-msgs` `#p-help` 用 `portal/kit` 拼；功能与口径照下面各条。

工单：
- 宽屏左列表（300 宽，「＋ 提交新工单」、列表卡、「帮助中心多半有答案」）右会话；手机列表与会话分两屏（`data-view`），会话与新建顶上「‹ 全部工单」只在手机显示。列表行：状态、分类、`last_reply_at`（今天时分 / 今年月-日，`listTime`）、标题、`#工单号 · N 条消息`。
- 会话底部三选一：已关闭的结尾块（已撤回「你撤回了这张工单」、已自动关闭「这张工单已自动关闭」、其余「✓ 这张工单已关闭」，都接「还有问题的话，提交新工单」）；`reply_blocked` 的一句话；回复框（textarea：Enter 发送、Shift+Enter 换行、组字回车不算）。「客服已回复」用 brand 色标签。
- 后台开了「须等客服回复」时以详情的 `reply_blocked` 为准换掉回复框（不在前端从消息推算）；`auto_closed` 显示「已自动关闭」。
- 按钮可见条件：撤回要未关闭且客服没回复过（与后端一致）；「问题已解决」照设计稿要未关闭且客服回复过（后端未关闭即可关，前端更严，两个按钮互斥）；回复只要未关闭（resolved 仍可回复、会重开）；`closed` 靠 `closed_reason` 分「已撤回」与「已关闭」。
- 新建、回复、关闭幂等（一次意图一把键）；撤回不幂等、请求体必须带 `{}`。撤回与关闭都先 ConfirmModal（关闭不可逆，设计稿没有确认框，按规则补上）。
- 客服按 D-F-2 统一显示「客服」不显示姓名；正文按后端要求 ≥ 10 字（报错照设计稿「请填写标题」「至少写 10 个字，客服才好判断」）；页头副标题不承诺「10 分钟内首次响应」（后端 SLA 普通 12 小时）；回车发送时输入法组字的回车不算。

帮助中心：
- 宽屏左列（带放大镜的搜索框、内置指南卡、目录卡、「没找到答案？直接问客服」）右文章卡；手机两屏（`data-view`），文章顶上「‹ 全部文章」只在手机显示。搜不到时目录卡里给提示与「提交工单」，底部那条藏起。文章卡与指南卡各自是页面上唯一的 `<article>`，指南里 h3 只有 App 名（浏览器测试 `portal-links.spec.ts` C8c 靠它）；指南末尾「还是不行？提交工单」。
- 可见性参数 `platform=any` 在列表、正文、反馈三处必须一致（`help/api.ts` 的 `HELP_QUERY`），不一致反馈会 404。
- 正文是纯文本 / Markdown 源码，只认「## 」行作小标题、空行分段，全部渲染成文本节点，不用 innerHTML。
- 内置一篇「在 App 里点一次更新」（不是后台文章）：`#/help?update=<ios|android|mac|windows>`，走查询参数不占文章 slug；目录最上面照设计稿是一张卡片「在 App 里点一次更新 / 换了链接、节点不对时先做这个 ›」，链到这台设备（`thisDevice()`）那一篇，指南页里用设备标签切换，标题上方写「内置指南」。内容在 `common/app-update.ts` 的 `APP_UPDATE`，`common/clients.ts` 推荐的每个 App 一段：在哪个页面、点哪个按钮、看到什么算成功，末尾给「删掉再添加一次」的退路；中文界面按钮带禁用词的写英文界面的名字。给 `clients.ts` 加 App 要同时加一段（守卫 `common.test.ts`「clients.ts 推荐的每个 App 都有一段」）
- 搜索交给后端 `q`（要匹配正文，列表拿不到正文）；「有帮助」按用户、文章、版本 upsert，天然幂等不带键；设计稿没有「没帮助」，照设计不加。

消息：
- 通知按浏览器本地日期分「今天 / 更早」（`groupByDay`，`sent_at` 为 null 归更早），时间写「N 分钟前 / N 小时前 / N 天前」，一周以外月-日（`noticeTime`）；图标按 code（`notificationIcon`，不认识的用铃铛）。未读：底色、粗标题、圆点。已读且没有去处的一条不可点。「全部标为已读」是文字按钮。
- 公告：置顶 brandSolid 标签在前，等级 critical 重要 / warning 注意 / notice 提示 / info 无标签，左侧色条同色；正文完整显示（pre-line，不截断）。
- 新站内信没有 SSE：外框铃铛 60 秒轮询 `['portal','notifications','unread']`（limit=1），消息页用 `['portal','notifications','list']`，写操作失效整个 `['portal','notifications']` 前缀让角标同步。

邀请返利：
- 页面自上而下：邀请卡（站点名 · 邀请、大号比例 + 一句话、三步、链接与两个复制按钮、用量说明、三格统计）、佣金卡（可用佣金大号数字、冻结说明、「转入余额」「申请提现」）、我的邀请码、佣金记录 / 邀请记录切换（Segmented，邀请记录带 `summary.invitees` 计数）。
- 「转入余额」与「申请提现」都开弹层：转入余额是大号金额 + 「转入后不能再提现」+ 再想想 / 转入余额，失败留在弹层里报错；申请提现是金额（带「全部 ¥x」）、最低额说明、收到哪里（多于一种方式才给单选）、收款账号、按钮写明金额。提现锁住（在途、不足最低额、没有开放方式）时「申请提现」禁用，原因写在佣金卡上；提现关闭时不画「申请提现」，佣金卡上写 `withdrawClosedHint`。
- 邀请链接是 `/?invite=<code>`，不能用 `/r/`（会撞 public 网关根下的订阅通配）。
- 邀请页列出全部个人邀请码（`InviteCodes.tsx`：状态、注册人数、访问量，active 在前），在后台设的上限内可再生成（`POST v1/me/invite/codes`，满了 409）；`invite` 仍是最早的有效码，邀请卡照旧用它。访问量按 IP 去重，只是参考。
- 可用佣金以账本为准（账本余额 − 在途提现），「转入余额」与「申请提现」用同一个数；后端同一时间只许一笔在途提现，`summary.withdrawing > 0` 或可用不足最低额时提现表单换成一句说明。
- 邀请卡标题按佣金概况的 `summary.direct_rate_bp`（直接邀请实得的万分比，多级分销时已乘第一级份额）与 `summary.scope` 写：照样稿大号「N%」加一句「好友每次付款，你都拿这么多佣金」，first_order 写「好友首单付款，你拿这么多佣金」，费率 0 只写「邀请好友注册」（`headlineParts`）（佣金按订单总额计）；邀请码有上限时写「这个邀请码已有 X 人注册，还能再邀请 Y 人。」；`risk_flag` 不展示给邀请人；不承诺「1–3 个工作日」，写「审核通过后打款」。
- 提现方式只从 `summary.withdraw_methods` 里选（目录与文案在 `src/core/withdraw-methods.ts`），USDT 地址前端只看形状、校验和以后端为准；只有人民币（10-16），页面不读 `currency` / `site_currency`：`withdraw_enabled` 为 false 时整段提现换成 `withdrawClosedHint` 的说明（解冻后自动转余额；关闭前已可提现的部分要自己点「转入余额」）。
- 佣金记录照设计稿：佣金条目标题「好友付款返佣」+ 灰色订单号，日期后附好友打码邮箱；`level` > 1 是下级好友的单，标题「第 N 级好友付款返佣」、不带邮箱（后端不给上级看下线邮箱，`from` 为空）；状态 可用 / 冻结至某日 / 已结算 / 已冲销 / 已驳回 / 已作废；转入余额「已完成」；提现标题「提现」+ 方式。设计稿里条目后的「套餐名 + 时长」后端没有，不显示。「付费好友」`paid_invitees` 只算第 1 级，和「邀请注册」同口径；`orders` 是条目数，含第 2、3 级。
