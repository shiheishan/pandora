# 合入前独立审查

根 CLAUDE.md「收回、集成与清理」要求：认证、权限、钱、迁移、节点通道的改动，合入前另派一个没参与实现的 opus 只读审查。这里是怎么派、查什么、怎么收。

## 什么时候必须审

| 改动碰到 | 例子 |
|---|---|
| 认证、会话、权限 | JWT、Redis 会话、登录失败计数、后台权限、找回密码、`identity` 模块、中间件 |
| 钱 | 订单、支付回调与验签、余额、账本、佣金、礼品卡、优惠码、`decimal` 计算 |
| 迁移 | `panel/db/migrations/` 任何新文件 |
| 节点通道 | `nodeapi/` proto、gRPC 流、mTLS 与证书、接入令牌、名单与纪元、pdnd 的 `panel/` 包 |
| 部署与发版 | `panel/deploy/`、`get.sh`、`.github/workflows/release.yml`、安装器 |
| 密钥与敏感数据 | 幂等缓存、日志、错误响应里会不会带出令牌、口令、后台前缀 |

一次合入涉及多个领域时，一个审查者看全部，清单合起来给它。改动很大时按领域分给两三个审查者并行，每个只看自己那份文件。

## 怎么派

1. 定范围：`git diff --stat <主线>...<分支>`，列出提交 sha 与要审的文件。
2. 照 `templates/review-brief.md` 填任务说明：范围、背景（这次改动要解决什么、已定的设计取舍）、本次涉及领域的检查清单（从下面「检查清单」挑）、报告路径。
3. Agent 工具，`model: opus`，后台运行。审查者没参与实现，只读：可以 `git log/diff/show`、grep、读文件、`bash -n`、跑 gitleaks 扫提交，不改文件、不提交、不 build/test。
4. 报告写到主目录 `.claude/runs/review-<日期>/<短名>.md`（被 git 忽略）。

## 检查清单

审查者逐项给结论（成立 / 有问题 / 不适用），不要只挑有问题的说。

**通用**
- 分层：handler 只绑定参数、调 service、写响应；GORM 只在 repository；模块不读写别人的表（`.claude/rules/panel-architecture.md`）。
- 错误、日志、req_id 走统一做法；错误响应和日志里没有令牌、口令、完整安装命令、后台前缀。
- 并发与事务：事务边界在 service；有没有先读后写的竞态、缺 `FOR UPDATE` 或唯一约束兜底；有界并发。
- 测试覆盖了失败路径，夹具是虚构数据、合库约束。
- 仓库公开红线：diff 里没有真实 IP、域名、密钥（跑 gitleaks，公开规则加主目录 `ops-local/gitleaks-private.toml`）。

**认证与权限**
- 每条新路由挂对了鉴权与权限中间件；后台路由不会被门户令牌访问，反之亦然。
- 会话吊销、过期、空闲超时仍然生效；限流与失败计数没被绕开。
- 用户只能读写自己的资源（按主体 id 过滤，不信请求里的 user_id）。

**钱**
- 金额全程 `decimal` / `NUMERIC`，没有浮点；舍入方式与位置明确。
- 余额变动只经只追加的账本；同一笔不会记两次（幂等键、唯一约束）。
- 支付回调验签、金额与订单核对、重放与乱序处理；回调失败不会把订单留在半状态。
- 佣金、优惠、礼品卡的口径与产品决定一致（记忆里的产品决定、`.claude/rules/module-*.md`）。

**迁移**
- goose 版本号接得上，有 Down，Down 真能还原 Up；不可逆的写明原因。
- 约束进库（NOT NULL、CHECK、UNIQUE、外键）；改 CHECK 前确认现存数据满足。
- 锁大表的 DDL 写了预检、`lock_timeout`、失败回滚；不用 AutoMigrate。

**节点通道**
- mTLS 校验链与身份；身份失效时节点端立刻停服（10-13 产品决定）。
- 名单与纪元：增量与全量的顺序、断线重连后不会少人或多人；proto 改动两端同步、字段编号不复用。
- 接入令牌一次性、有过期、不进日志和幂等缓存。

**部署与发版**
- 脚本 `set -euo pipefail`、变量加引号、临时目录权限、先校验后解包；`curl` 走 https 且失败即停。
- workflow 权限最小化，`${{ }}` 经 env 进 `run`，发布只在 `v*` 标签上发生。
- 升级路径能回退或写明不能回退（RUNBOOK）。

## 报告格式

开头写审查范围（分支、提交、读过哪些文件、跑过哪些核对）和一句总结论（有没有阻塞）。然后三档：

- **阻塞**：合入会出安全、钱、数据错误，必须先修。
- **应改**：真问题但不致命，这次一并修。
- **建议**：可读性、更好的写法、以后再做的事。

每条：位置（`文件:行`）、失败场景（具体的输入或状态 → 错在哪里）、建议改法。拿不准的写「待核实」和要核实什么，不要当结论。

## 收回

1. 主 Agent 读报告，逐条核对代码（报告也可能错）。
2. 阻塞与应改：自己改或派回原来那一块；改完在原报告末尾追加「处理」一节：每条 → 提交 sha 或不改的理由。
3. 建议里不做的，记进 TASKS.md「发现与决定」；需要产品判断的汇总给用户。
4. 改动大到换了设计的，再审一遍（可以续用同一个审查者，SendMessage 保留上下文）。
5. 收尾表里写：审查 | opus 只读 | 结论 | 报告路径。
